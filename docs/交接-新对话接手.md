## 四、已经查清并修掉的根因（附证据）

### 1. 跨章落点与进度恢复失效（同一根因）

`promoteChapter` 里有一句把位置重置成"该章第一页"。真机数据库佐证：

```
reading_progress: ('3GTS', 'Issue 2', pageOrdinal=0)   ← 读者读到第 3 页，存的却是第 0 页
```

一个重置同时造成"跨章后回到第 1 页"与"重开回到第 1 页"。已删除该重置；
落点改为"过渡项在新列表中的下一个位置"（必然是目标章第一页）。

**注意这里出过一次回归**：中途我改成"按项身份找回位置"，而那个身份**正是过渡项自身**，
于是提升后落回过期位置，读者被送回上一章、过渡页也看不到。
现在落点逻辑抽成纯函数 `resolveLanding`，按「页身份 → 过渡项后继 → 章首」的优先级
依次尝试，并有单测钉住。

### 2. 直接打开章节闪退 = OOM，根因在库的解码器

崩溃栈稳定：

```
OutOfMemoryError: Failed to allocate a 8294416 byte allocation
  at com.davemorrissey.labs.subscaleview.decoder.Decoder.init(Decoder.kt:54)
  at SubsamplingScaleImageView$TilesInitTask.doInBackground(:2774)
```

`javap -c` 反编译得到的结论：

- `Decoder.init` 无条件调用 `InputProvider.openStream()`，把**整张图**解码进一个 `ByteBuffer`
  再转 byte[]；那笔 8294416 字节就是它。
- 位图格式**硬编码 `ARGB_8888`**，因此 `setPreferredBitmapConfig(RGB_565)` 与
  `setMaxTileSize` 对它**完全无效**——这解释了为什么改成 565 后失败字节数一模一样。
- `TilesInitTask` 里是硬编码 `new Decoder(...)`，`decoder` 字段 private 无 setter，
  **除了反射没有干净的注入点**。
- 该解码器来自传递依赖 `ca.mpreg:imagedecoder:9`，native 库 `libimagedecoder2.so`
  每种 ABI 16–19MB（四 ABI 约 66MB，是 APK 达 90MB 的来源）。

已做的三层降内存（**未验证是否消除**）：同一页只 `setImage` 一次、`doOnLayout` 后载图、
超过长边 3000 的页先降采样再编码成 PNG 交给库（走公开的 `ImageSource.provider`）。

### 3. 详情页看不到页数 = 数据缺口（已定位并部分修复）

按卡片可用性拆分后的实际规模：

| pageCount | AVAILABLE | STALE |
|---|---|---|
| 未回填 | **4698** | 658 |
| 已回填 | **6** | 0 |

可读的 4704 个章节里只有 6 个有页数。原因是页数只在"打开过那一章"时写入。
已实现**按需、有上限**的回填（每次进详情页最多补 8 章）。

### 4. 被否掉的假设（避免重复调查）

- **数据库没有结构性损坏**：孤儿章节、重复 `documentId`、失效进度引用、越界页码全为 0；
  3GTS 两章数据完全正确。所以"数据库缺失导致闪退"不成立。
- **44 部"章节数声明不符"全部是 `STALE` 卡片**（界面不显示），属历史遗留。
- **`coverChapterId` 失效只有 4 部**。
- **模拟器渲染问题（页面不画、下层透出）是 MuMu 特有**：语义树里只有阅读器、
  而截图却大部分是下层页面；给根布局染洋红、给引擎视图染青的采样数都是 **0**；
  **真机上阅读器完全正常**。不要在此继续投入。

## 五、跨章编排：这一轮查清的真实结构

这一轮在跨章上连续踩了五个坑，每个都只在真机/逐页点按时才暴露。**先读这一节**，
否则很容易重犯（前四个坑我各犯过一次以上）。

### 5.1 项列表的形状

```
[反向过渡] 上一章页 … 当前章页 [正向过渡] 下一章页 … [正向过渡] [到底过渡]
```

- **每一个跨章边界恰好一个过渡项**，且唯一属于某一章：章 i 的**正向**过渡排在它自己页
  之后（只在 i 之后还有章时存在）；章 i 的**反向**过渡排在它自己页之前（只在 i 之前还有
  章时存在）。于是顺着阅读顺序往后翻只会经过正向过渡。
- 窗口是**从当前章向两侧展开**的，因此窗口远端的过渡项一律归属"更近的那一章"。
  这样同一个边界在不同窗口下算出的键完全一致——**这是 `resolveLanding` 能在窗口变化后
  仍找到它的前提**。
- 反向过渡位于**列表下标 0**（反向窗口在最前）。因此它再往回翻不会越界，`settleOn`
  的"落在过渡项上就停住"对它**不适用**——停在那里读者会永远卡住（本轮真实症状：
  一直显示"上一章"而翻不动）。反向过渡到达即提升上一章，落点取上一章**最后一页**。

### 5.2 五个坑

1. **提升章节时从零重建窗口**（`ViewerChapters(current = promoted)`）会丢掉窗口里其他章
   的页清单，而它们正是接下来要显示的内容。症状：每跨一章都要重新等载入，已就绪的下一章
   也显示"正在载入"。**改为保留整个窗口、只替换 `current`。**
2. **`applyWindow` 用快照算结果、再拿它和实时状态比较**（`if (rebuilt != chapters)`）。
   当"实时页清单已变、快照未变"时整次写入被跳过，刚加载好的页永远进不了项列表。
   **改为读取、补齐、排序、构建项列表、写入全部在同一个 `_state.update` 内完成。**
3. **窗口可能不自洽**：某章被放错一侧或重复时，项列表会把某一页画成过渡页，末页误报
   "已是最后一章"而后面其实还有章。新增 `ViewerChapters.sanitized` 在构建项列表前统一
   校正，并有单测钉住 `withAdded`（补）与 `withChapter`（替换）的分工——这两个方法混淆过一次。
4. **分页器把"我们挪的位置"回放成"读者翻页"**，造成来回撞墙。位置抑制放在 `PagerReader`
   内做（区分程序化滚动与读者翻页）。**不要**用"记住上一次处理过的下标"这种全局去重：
   它会把读者恰好翻到我们曾挪到过的位置也一并丢掉。
5. **分页器归位 effect 的 key 不能只带项数**。窗口重排会让某一项的下标变而项数不变
   （提升章节后当前章页面从下标 9 变到 1 就是这种），于是分页器停在旧下标上——那个下标
   现在指向另一页，"往回翻"跳到不相干的位置。key 用**当前位置的项身份**。

### 5.3 预载预算与窗口扩张

- 「预载页数」默认 9，**过渡页也算一页**。跨一章的代价 = 1（过渡页）+ 该章页数。
- 页数未知的章是**边界章**：放进来并要求枚举一次。没有这一步，第一部打开的漫画会因为
  "谁都不知道有几页"把窗口算成空的，末页只能显示"已是最后一章"，而后面其实还有几十章。
- 预载进度会**比窗口慢一步**（规划用的是已知页数，而页数要加载完才知道），因此
  `applyWindow` 除了规划覆盖的章之外还会再接**一格边界章**，逐格追上预载进度。

### 5.4 仍未解决

短章夹具（一章只有 3 页）上偶尔仍会看到"下一章 · 正在载入…"一闪。长章夹具
（76/54/29 页）上未复现，疑似只影响"一章只有 3 页"这种极端比例。已排除的方向：
窗口自洽性、快照/实时比较、分页器归位、邻章加载顺序。下一步建议在
`applyWindow` 里打印"窗口 + 每章页数 + 项列表"，配合逐页点按定位那一瞬间。

## 八、工作方式上值得注意的几点（避免重犯）

1. **取设备数据库的 `exec-out` 路径不稳定**，会静默截断成残片并报
   `database disk image is malformed`。**校验 `PRAGMA integrity_check` 再用**，
   否则会把坏拷贝当成设备真损坏（我误判过一次）。
2. **改代码前先确认改的是哪一层**。我在跨章落点上连续改错两次：
   第一次猜"身份会丢失"（其实不会），第二次"按身份找回"（身份就是过渡项）。
   最终靠**加单测**才发现真实结构（过渡项只插在当前章之后，往回翻走的根本不是过渡项）。
3. **"状态被写坏"比"算法算错"更常见，而且更难看出**。本轮五个坑里有四个是并发写入
   与快照过期造成的，症状全都伪装成"落点算错了"。可复用的判别方法：
   **打印出实际的窗口与项列表**（而不是只看屏幕），一看形状就知道是哪一类。
   我前面花在推理上的时间远多于加上那两行日志之后花的时间。
4. **不要用"全局记住上一次的值"来去重**。`lastSettledIndex` 那版把读者恰好翻到我们
   曾挪到过的位置也一并丢掉了；正确的做法是在**能区分来源的那一层**去抑制
   （分页器知道哪次滚动是自己发起的）。
5. **先量规模再判断严重性**。"5356 个章节没有页数"听起来像脏数据，
   按可用性拆开才发现是**可读内容上的 4694 个缺口**，性质完全不同。
6. **不确定就标注不确定**。真机不在时我把渲染问题写成"模拟器特有"是基于
   语义树与截图矛盾的实验，并明确写了"未确认"；后来真机验证确实正常。
7. **在模拟器上造夹具比在真机上试快得多**。用 `adb push` 放"4 章 × 3 页"这种极端比例

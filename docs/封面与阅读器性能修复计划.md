## 3. D3 定稿：按上游做法，**不做整图解码 + 重编码**

调研 `.research/mihon` 与 `.research/EhViewer` 后确认：两家都**不切分长图**，也都**不做"整图解码再重编码"**，而是在**解码时**按「视图/屏幕尺寸」降采样。

### 3.1 EhViewer：解码尺寸由屏幕短边决定

`app/src/main/kotlin/com/hippo/ehviewer/image/Image.kt:93-113`

```kotlin
private val sizeResolver = with(appCtx.resources.displayMetrics) {
    val targetSize = minOf(widthPixels, heightPixels) * 4 / 3   // 屏幕短边 × 4/3
    SizeResolver(Size(targetSize, targetSize))
}
...
size(sizeResolver)
scale(Scale.FILL)
precision(Precision.INEXACT)      // 允许非精确采样（2 的幂）
maxBitmapSize(Size.ORIGINAL)
allowHardware(false)
```

即：**任何一页都按"屏幕短边 × 4/3"解码**。在 1080×2400 上目标 1440，2550×3299 的页会以 `inSampleSize=2` 解成 1275×1650（≈8.4MB），而不是 33.7MB；没有重编码，也没有切图。

### 3.2 Mihon：分页交原始流、条漫按视图尺寸解码 + `largeHeap`

- `app/src/main/AndroidManifest.xml:43` → `android:largeHeap="true"`
- 分页（`ReaderPageImageView.kt:294-299`）：`setImage(ImageSource.inputStream(data.inputStream()))`，把采样交给 `SubsamplingScaleImageView`（它按**视图**算 base layer 的 sampleSize）；配 `setMinimumTileDpi(180)` / `setMinimumDpi(1)`。
- 条漫（同文件 `301-323`）：Coil `ImageRequest … .size(ViewSizeResolver(view)).precision(Precision.INEXACT).customDecoder(true)`，即**按视图尺寸解码成位图**再 `ImageSource.bitmap(...)`。
- 其自定义 Coil 解码器同样按请求尺寸采样：`app/.../data/coil/ImageDecoder.kt`（`options.size.widthPx/heightPx` + `DecodeUtils.calculateInSampleSize`）。

### 3.3 LM-Reader 的结论

现状那套"整图解码 + PNG 重编码"既不是上游做法，也没达到目的：本轮实测 3299px 时 `sample` 恒为 1（阈值判断 off-by-one），于是付出 33.7MB 分配 + 全尺寸 PNG 编码（秒级）却**一点都没降采样**。

改为（与 EhViewer 同构，也符合 Mihon 条漫路径）：

1. `inJustDecodeBounds` 读原始尺寸（只读文件头，便宜）；
2. 目标长边 `targetLong = min(viewW, viewH) * 4 / 3`（按 EhViewer 的 4/3；做成常量便于以后调）；
3. 若 `longest <= targetLong` → 原样把流交给引擎（不多搬一个字节，保留引擎的分块解码）；
4. 若 `longest > targetLong` → 用 `calculateInSampleSize` 的 2 的幂**解码一次**得到视图级位图，交给 `ImageSource.bitmap(...)`。
   - 这条路径**绕开** `ca.mpreg.imagedecoder` 的 `Decoder.init`（`docs/交接-阅读器真机缺陷.md:46-76` 记录的 OOM 根因：整图 `ByteBuffer` + 硬编码 ARGB_8888），峰值从"33.7MB ByteBuffer + 33.7MB 位图"降到"一张 8.4MB 位图"；
   - 代价：该页放大超过采样分辨率时是放大插值。EhViewer 接受同一代价（`Precision.INEXACT`），Mihon 条漫路径同样接受。
5. 以上全部在 `Dispatchers.IO` 上做；预取命中时也不再 `readBytes()` 把整页读进堆（只读头部定尺寸，再按需二次开流）。

## 4. 封面改为「滚动时懒加载」

规则（按用户口径）：扫描只写路径 → 图库/书架/搜索结果**滚动到可见**才取（一次一批 30 项）→ 取过一次（成功或失败）落库标记、**不再取第二次** → 打开详情页点「更新章节」**必取**。

- **数据层**：`mangas` 新增 `coverProbedAt INTEGER`（null = 从未探测；一个字段同时表达"成功"与"确实没有"）。迁移 `v3→v4`：新列 + `coverProbedAt = updatedAt WHERE coverDocumentId IS NOT NULL` + B6 顺序校正。迁移显式登记（本仓库禁止破坏性迁移）。`MangaCard` / `toCard()` / 9 处投影查询补列。新契约 `markCoverProbed(...)`。
- **`core:storage` 新增 `CoverResolver`**：多章节 → 按 sortKey 取第一章，是 `IMAGE_DIRECTORY` 就列目录取自然序首图（前 3 章内找不到即放弃）；单章节 → anchor 目录本身即章节。`firstImageInNaturalOrder` / `isSupportedImage` 从 `MetadataBackfillWorker` 提到 `core:index` 复用。
- **UI**：`LibraryScreen` / `BookshelfScreen` 用已有 `gridState/listState` 上报可见项 → `onCardsVisible(ids)`；VM 内有界队列 + 并发 2，只入队 `coverProbedAt == null`，队列上限 200 且"最新可见窗口优先"，解析一条即更新内存 + 单行落库，`paging.reset()` 时取消队列；与 `loadMore()` 完全解耦。详情页进入时未探测则探一次；`syncChapters()` 成功后**强制**重取并刷新。

### 8.4 新增：阅读设置里的「加载原图」开关

用户要求增加一个"加载原图"开关，用来自己决定**解码多少像素**（与"画多大"无关）。

- 设置项：`ReaderSettings.loadOriginalImage`（默认 **关**），持久化键 `loadOriginal`；
- 入口两处：**设置 → 阅读器**（`ReaderSettingsScreen`，带代价说明）与**阅读中的设置面板 → 通用 → 分页**
  （`ReaderSettingsDialog`）。两处共用 `ui/common/LabeledSwitch`；
- 接线：`EnginePageView` 在开关打开时把解码目标设为 **0**，`planPageDecode` 对非正目标一律
  "原样交流"——即一个像素都不减；关闭时仍按"屏幕短边 × 4/3"决策；
- **切换立即生效**：解码目标进了 `LaunchedEffect` 的键与视图 tag，所以当前页会按新策略重新解码一次，
  不必退出重进。

模拟器实测（同一页 `2550×3299`，同一个进程内现场切换）：

| 加载原图 | 送进引擎的像素 | Java Heap | TOTAL PSS |
|---|---|---|---|
| 关（采样到 1275×1650，RGB_565） | 约 4.2 MB | **15.2 MB**（与"不进阅读器"的应用基线 15.2MB 持平） | 167 MB |
| 开（原图 2550×3299） | 约 33.7 MB + 库内部 ByteBuffer | **138.9 MB** | 316 MB |

同一页差 **124MB**，这就是这个开关的取舍量级；也说明它不是"摆着没接线"的控件。

### 8.5 仍然保留的已知限制

- 详情页每次最多回填 8 章的页数（B11）；
- 归档章节（zip/CBZ/PDF）仍然没有封面与页清单，属于 P2；
- 混合目录（既有直接归档、又有图片子目录）按既有规则只把归档当章节，因此这类卡片没有封面；
- 真机（小米 14 Ultra，1080×2400）尚未验证：那里的解码目标是 1440，`2550×3299` 会走"原样交流"分支（与 Mihon 分页模式一致），需要实机确认观感与内存。

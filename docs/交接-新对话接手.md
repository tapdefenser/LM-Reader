## 一、项目与目标

Android 本地漫画阅读器，Kotlin + Compose Material 3，手写 `AppContainer` 依赖装配
（无 Hilt）。参照基准是本地克隆的 Mihon 源码（`.research/mihon` @ `f52d890`，Apache-2.0）。

用户的要求与已定的范围：

1. **除翻译遮罩外照搬 Mihon 阅读器**；
2. **采纳 Mihon 用的图片引擎**，而不是复制它的 Kotlin 源码；
3. **页内进度照搬 Mihon**：只存页码，`reading_progress.intraPageRatio` 恒为 0；
4. **ZIP / CBZ 页源暂缓**。

## 四、阅读器的核心设计：把"跨章"降级为位置

**这是整个阅读器最重要的一条，先读完再动它。**

阅读器展示的是一条**线性列表**：

```
… issue1 的页、[过渡页]、issue2 的页、[过渡页]、issue3 的页 …
```

**过渡页只是这条线上的一个普通位置**，和"一页图"本质相同——只是显示的不是图片而是
"已读完 issue1 / 下一章 issue2"。由此推出：

- **翻页就只是前后移动一格**。滑动、点按区域、音量键、滑杆、上一章/下一章按钮全部
  汇聚到 `move(delta)`；当前在哪一章由"当前项属于哪一章"**反推**。
- **没有"跨章"这个事件**，也没有"提升章节"。
- **过渡项没有方向**：`ReaderItem.Transition` 里没有 `forward`，键只由前后两章决定，
  往前翻与往后翻遇到的是同一个项。
- **窗口在阅读过程中固定**，只在读者走到边缘章时才向那一端补一批；补的时候按项身份
  重新定位（`reanchorIndex`），因此画面不跳。**因为窗口不重建，所有项的下标不变，
  "翻页跳到别的页"在结构上不可能发生。**
- **列表里只放"已知页数"的章**。还没加载完的章完全不出现——否则会插出一个悬空的
  过渡页（甚至两个挨在一起）。

### 已废弃的方案（**不要回去**）

前几版都栽在同一个念头上：**把"跨章"当成事件**。这些机制全部删掉了（净减 713 行）：

| 删掉的机制 | 它造成的问题 |
|---|---|
| `promoteChapter`（碰到过渡页就提升章节、重建列表） | 下标整体变化而分页器停在旧下标 → **跳页** |
| `landingAfterTransition` / `resolveLanding`（两套下标间换算落点） | 换算一错就落到不相干的页 |
| `forward` 方向标志 + 两套过渡项 | 同一边界两个键，窗口一变就找不到 |
| `pauseOnChapterTransition`（到达后停不停的开关） | 新模型里过渡页本来就占一格，开关没有意义 |
| `sanitized()` 脏窗口校正 | 窗口不再被重建，就没有"脏窗口" |
| 分页器的"程序化滚动抑制" | 不再重建窗口 → 不需要把位置挪来挪去 |
| `pastStartChapter`（往回翻越界时提升上一章） | 不存在"越界"，往回翻就是上一个项 |

**如果你发现自己在加回其中任何一个，先回来读这一节。**

### 预载

- 「预载页数」默认 9（范围 2–19），**过渡页也算一页**：跨一章的代价 = 1 + 该章页数。
- **前后各一半预算**（9 → 往后 4、往前 5）。预载的价值在于"从哪一页打开"，
  读者从第 37 页打开或想往回翻时，前面几页也该是就绪的。
- 页数未知的章是**边界章**：必须收进来**且同时被加载**（`chaptersFor`）。
  曾经出现过"规划算出了边界章、但没人去加载它"，于是它页数永远未知、窗口再也长不起来
  ——真机上表现为只剩当前章、末页显示"已是最后一章"。
- 末章判定用**整部的最后一章**，不是窗口的最后一章。
- 字节预取只落**磁盘**（`PagePrefetcher`），不压堆：真机堆上限 256MB，
  解码一页就已经吃过整图分配的亏。
- `PagerReader` 的 `beyondViewportPageCount = preloadPages / 4`（上限 2）：
  相邻页保持已解码状态，落页时不会闪。

## 五、已经查清并修掉的根因（附证据，避免重复调查）

### 1. 跨章"闪黑一帧" = 我自己的一行 composition key

```kotlin
key(state.chapters?.currentChapterId, state.readingMode) { ... }   // ← 旧写法
```

`currentChapterId` **正好在跨章那一刻变化** → 整棵阅读组件树被销毁重建 → 所有已显示
页面的引擎视图一起重建、解码从头再来，**其中就包括读者正在看的那一页**。

**日志证据**：修前跨章瞬间 `090/089/088/001` 四页在同一个 8ms 内 `setImage`。
修后只重建真正需要的那一页。**解码本身只要 35–70ms，不是瓶颈**——这一点用日志量过，
不要被"解码慢"带偏。

章内该 key 不变，所以章内不闪。现在只按 `readingMode` 重建（分页 ↔ 条漫是两套实现）。

### 2. 直接打开章节闪退 = OOM，根因在引擎的解码器

```
OutOfMemoryError: Failed to allocate a 8294416 byte allocation
  at com.davemorrissey.labs.subscaleview.decoder.Decoder.init(Decoder.kt:54)
```

`javap -c` 反编译的结论：

- `Decoder.init` 无条件把**整张图**解码进 `ByteBuffer` 再转 byte[]；那笔 8294416 就是它。
- 位图格式**硬编码 ARGB_8888**，因此 `setPreferredBitmapConfig(RGB_565)` 与
  `setMaxTileSize` **完全无效**——这解释了"改成 565 后失败字节数一模一样"。
  （那行无效的静态配置已删掉，留着只会让人误以为内存已被限制住。）
- `TilesInitTask` 里硬编码 `new Decoder(...)`，`decoder` 字段 private 无 setter，
  **除反射没有干净注入点**（已否决反射：release 的 R8 可能改名）。
- 解码器来自传递依赖 `ca.mpreg:imagedecoder:9`，native 库 `libimagedecoder2.so`
  每种 ABI 16–19MB（四 ABI 约 66MB，是 APK 约 90MB 的来源）。

现有对策：同一页只 `setImage` 一次、`doOnLayout` 后载图、超过长边 3000 的页先降采样
再编码成 PNG 交给库（走公开的 `ImageSource.provider`）。**近期真机未再复现。**

若还要压内存，两条未走的路：
1. 反射注入自定义 `ImageRegionDecoder`（接口公开，可用 `BitmapRegionDecoder` 做**真正的
   区域解码**，顺带去掉 66MB native 依赖）；
2. 让库拿到**可随机访问**的输入（临时文件），看它是否因此改用区域解码。

### 3. 详情页看不到页数 = 数据缺口（已按需回填）

| pageCount | AVAILABLE | STALE |
|---|---|---|
| 未回填 | **4698** | 658 |
| 已回填 | **6** | 0 |

页数原本只在"打开过那一章"时写入。已实现**按需、有上限**的回填
（`PAGE_BACKFILL_LIMIT = 8`，每次进详情页最多补 8 章）。

### 4. 搜索框"每次只能输入一个字符、光标跑到前面"

防抖回调把**延迟之后**的查询写回了输入框的 `value`：

```kotlin
queryFlow.debounce(300).collect { query -> _state.update { it.copy(query = query) } }
```

用户连打三个字符时，300ms 后那次发射带的是旧文本，写回 `value` 会覆盖刚输入的内容，
光标同时被重置到开头。**修法**：拆成两个字段——`query` 只由 `onQueryChange` 同步更新
（输入框的 value），`appliedQuery` 是防抖之后的（只用于查询与空状态文案）。

另外 `singleLine = true` **只管 IME 回车行为、不限制行数**，要文字不换行必须同时写
`maxLines = 1`。

### 5. 被否掉的假设（不要重复调查）

- **数据库没有结构性损坏**：孤儿章节、重复 `documentId`、失效进度引用、越界页码全为 0。
- **44 部"章节数声明不符"全部是 `STALE` 卡片**（界面不显示），属历史遗留。
- **`coverChapterId` 失效只有 4 部**。
- **"模拟器上阅读器不画、下层透出"是 MuMu 特有**：语义树里只有阅读器而截图是下层内容，
  诊断色采样为 0；**真机完全正常**。不要再投入。

### 5. 阅读器"最多只能读到第 4 章" = 加载链在第一次加载完成后就断了

**症状**：从第 1 章开始读，能读到第 4 章，之后再也翻不下去（像被墙挡住）。

**根因**（`ReaderViewModel`，两处配合出来的）：

1. `rebuild()` 只**重排窗口**、不请求加载。它唯一的作用是"把已加载的章重新拼成项列表"。
2. `loadOne()` 的守卫是 `if (loadJobs.containsKey(id)) return`，而 **`loadJobs` 里的条目
   从来没有被移除过**。于是 `loadJobs` 悄悄变成了"曾经请求过"的集合。

进入第 1 章时规划出 2/3/4 三章并请求加载；三章都完成后 `chaptersToLoad` 仍然返回
2/3/4，全部命中守卫被跳过 → **没有任何新请求**。窗口永远停在 `[1,2,3,4]`，
正好就是"最多 4 章"。推进到第 5 章需要有人**在换章时重新规划**，而当时没有任何路径会做。

**修法**（三处，缺一不可）：

- `rebuild()` 里补上 `loadNeighbors()`：**规划与加载必须一起发生**（这是核心）。
- `loadOne()` 的守卫语义改成两个不同的判断：`loadJobs` 里已有 = 正在加载、别重复排队；
  `loaded` 里已有 = **已经有结论**（成功或失败）、不必再来。失败章只能由「重试」显式重来，
  否则每次 rebuild 都会重试失败章，变成无限重试。
- `loadJobs` 的条目在 `finally` 里移除；`retryFailedChapters()` 先把失败结论从 `loaded`
  里摘掉再重试（不摘掉的话守卫会让"重试"变成空操作）。

同时把 `buildWindow()` 的窗口**有界化**：只保留"当前章 ± 预载范围"内的已加载章。
旧写法"保留所有已加载章"会让窗口随着阅读无限增长——上千章的漫画会把整个目录的页清单
堆进项列表，而且 `nearWindowEdge()` 会失效（它假设窗口约等于预载范围那么大）。
被放掉的章**只是不显示**，页清单仍在 `loaded` 里，往回翻立刻可取回、不重新读盘。
另外 `lo/hi` 两侧各留一格（`currentIndex ± 1`）：过渡项只有"后一章也在窗口里"才会生成，
少了这一格读者翻到本章末页会直接卡住。

**真机/模拟器验证方法**（可复现）：夹具要有 **> 4 章**，现有夹具原来最多 4 章，正好卡在
边界上复现不了。给模拟器上的 10 章夹具做定点测试：

- 进入第 1 章 → 右侧点击 17 次 → 应落在第 5 章附近（旧版会停在第 4 章末）。
- **点击有效率取决于间隔**：0.35s 时约一半点击会被分页动画吃掉，0.9s 时 1:1。
  因此"数点击次数"不可靠，要**让控制栏保持可见**并逐步核对顶栏显示的章节名。
- 实测：第 4 章第 1 页（第 12 格）→ 点 8 次 → 第 6 章第 1 页（第 20 格），正好 8 格；
  继续走到"已是最后一章 / 已读完 Chapter 10"。

### 6. 长阅读 OOM = **我自己引入的每帧重建环**（不是引擎的固有代价）

> 这一节推翻过我自己的一个错误结论，两版都留着：**错在哪、怎么查出来的**比结论本身更值钱。

**症状**：连续阅读（约 60 次翻页）后进程被 `SIGABRT` 杀掉，崩溃缓冲里是：

```
JNI DETECTED ERROR: JNI FindClass called with pending exception
java.lang.OutOfMemoryError ... in call to FindClass
  from ca.mpreg.imagedecoder.ImageDecoder.new  ← Decoder.init 调起
```

**第一版结论（错）**：我做了 `git stash` 对照，看到原始版 native 也涨到 184MB，就下结论说
"这是引擎整图解码的既有代价，不是回归"，还写了一张对照表。**错在只看了内存总量，没有同时数
"事件次数"**——内存涨可以是"少量页面占很多内存"，也可以是"同一批页面被反复解码扔掉"，
两者用 `dumpsys meminfo` 分不出来。用户的质疑一针见血：**按设计内存里只该有
`preloadPages/4`（≤2，即约 5 页）个解码视图，怎么可能吃满？**

**真正的根因**：`buildWindow()` 有界化之后，**窗口内容依赖当前章**，而当前章是从"落页回报的
下标 → 项"反推的，于是形成正反馈环：

```
落页在过渡项(index 3) → 它 chapterId 归后一章 → 当前章 = ch2
  → 窗口按 ch2 重算 → 项列表 11 → 15 项
  → 分页器（reverseLayout 右到左）的「偏移 ↔ 下标」映射抖一格
  → 落页回报 index 2（15 项表里是 ch1 的末页）→ 当前章 = ch1
  → 窗口按 ch1 重算 → 项列表 15 → 11 项 → 回到第一步
```

原始版没有这个环，只是因为 `buildWindow()` 保留**所有**已加载章，两个相邻当前章算出的窗口
一样大，抖不出来——**它一直在，原来的窗口写法把它盖住了**。实测这个环每秒重建 80 多个引擎
视图、每次 `setImage` 都整图解码一次，native heap 被顶到 300MB 以上。

**怎么查出来的**（这套方法请沿用）：

1. **在 `EnginePageView` 里数"同时活着的引擎视图"**：加一个 `AtomicInteger`，
   factory 里 `+1`、`DisposableEffect.onDispose` 里 `-1`，并把每个视图的
   `System.identityHashCode` 打进日志。结论：**存活视图一直是 3~4 个**（上界守住了），
   于是"引擎按视图泄漏"被排除。
2. **数 `setImage` 的次数**：同一页 `made=111`、约 18ms 一轮、交替两个页 id、
   每次 `view=` 都是**新实例** → 不是泄漏，是**每帧重建**。
3. **在状态机上打日志**（`rebuild` / `settleAt` / 窗口章序列 / 项数 / 下标）：
   一次翻页后 `rebuild` 跑了 **1756** 次、`settleAt` **1759** 次，日志里
   `items=11 ↔ items=15` 来回翻 → 环在哪一目了然。
4. **对照实验要控制变量**：原始版**空等 10 秒 `setImage` 恒为 5、每页 `made=1`**；
   修复版同一场景 12 秒内涨到 1487 次 → 差异归因才成立。

**修法**（三处，都在 `ReaderViewModel` / `ReaderChapters`）：

| 修法 | 作用 |
|---|---|
| `chapterEnteredBy(item)`：**过渡项不算换章**（只有 `PageItem` 才算进入它那一章） | 断掉环的第一步。过渡项的 `chapterId` 按设计归后一章（为了 key 稳定），但"站在两章之间那一张上"不等于"已进入下一章"。下一章本来就被"边界章"规则收进窗口并加载了，不会卡住跨章读 |
| `settleAt` 里 `if (chapterChanged && nearWindowEdge()) rebuild()` | 窗口只依赖"当前章 + 设置 + 已加载章的页数"，**同章内翻页不需要重新规划**。原来每次落到窗口边缘都重建，环里就是 1700 多次无谓重建 |
| `writeItems`：窗口的**章 id 序列没变就完全不改 `items`**（连实例都不换） | 分页器只在项列表真的变了时才需要重排；白换一次实例就白抖一格 |

**修复后实测**（同一场景）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 翻 1 页后 12 秒内 `setImage` | 752 次且持续增长 | **5 次，恒定** |
| 整个 10 章会话的 `view+` | 20 次翻页就 163 次 | 约 39 次翻页共 **40 次**（≈1:1） |
| native heap | 280MB 且每 17ms 涨一轮 | 逐页采样在 **77–165MB** 间波动（3~4 个存活视图），不再单调爬升 |
| 跨章能力 | — | 第 1 章走到第 10 章 + "已读完 Chapter 10" 正常 |

**结论**：内存现在由"存活视图数（≈`preloadPages/4` + 1）× 每页整图解码"决定，这与设计一致。
`loaded` 里的页清单（纯元数据，很小）只增不减，暂不构成问题。

设备参数（对照用）：`dalvik.vm.heapgrowthlimit=192m` / `heapsize=512m`；吃内存的是
**Native Heap**（Android 上 Bitmap 像素算在 native 侧，`Graphics` 一栏是 0），Dalvik 只用了 ~77MB。

**若还要继续压**（尚未做）：`MAX_ENGINE_LONG_EDGE`（现 3000）调小、`adjacentPagesAlive`
（现 `preloadPages/4`，上限 2）调小。压之前请用上面的"事件计数 + 逐页采样"方法量，
**不要只看内存总量就归因**。

## 六、详情页：自动更新章节 + 章节排序

- **进详情页自动更新一次章节**，且**不弹提示**（后台行为每次弹一条是噪音；
  但**失败一定要报**——列表可能是旧的，用户得知道为什么）。
  放在 `init` 而不是 `reload()`：`reload()` 也会被「重试」与**从阅读器返回**触发，
  每次返回都重新枚举目录是浪费（100 章的漫画就是 100 次目录枚举）。
- **章节列表表头有排序按钮**，显示**当前**顺序（「从旧到新」/「从新到旧」），点一下切换。
  全局偏好 `AppPreferences.chapterSortDescending`，默认 false。
  排序在 UI 层派生（`MangaDetailUiState.sortedChapters`），不在仓储层做——顺序是纯展示决策。

## 七、滚动条（`ui/common/ListScrollbar.kt`）

图库（列表 + 网格）与书架各接一个。这块踩坑最密，**改之前请读完**：

| 要点 | 为什么 |
|---|---|
| 视觉条 4dp，**触摸区 28dp**，手势挂在**触摸区**上 | 一开始把 `pointerInput` 挂在了里面那条 4dp 的视觉条上，于是有效触摸区一直是 4dp——**外面写多少都没用**，真机上完全摸不到 |
| 触摸层**只覆盖右侧一条窄带** | 试过"铺满整个列表区"（想着命中更可靠），结果**整个列表的点击都失效**，连屏幕正中间的卡片都点不开。Compose 里重叠的兄弟节点**不是"不消费就穿透"** |
| 组件**自己贴右侧**，不靠调用方写 `align` | 曾经把调用方的 `Modifier.align(Alignment.CenterEnd)` 删掉，滚动条跑到了屏幕左边 |
| 颜色取 `MaterialTheme.colorScheme.onSurface` | 曾写死 `Color.White`，而本应用配色**跟随系统**——浅色模式下白叠白，等于隐形 |
| **常驻**显示，不做自动淡出 | 曾做"滚动时才显示、停手 900ms 淡出"，读者停下手指再去找它已经没了 |
| 位置按**行**估算，两端用**精确锚点** | 按"项数 × 平均项高"算，网格里 7 项被当成 7 行、内容长度虚高约 3 倍——**内容占不满一屏却画出了滚动条**。行是从可见项自己推出来的（共享同一 `offsetY` 的项属于同一行），列表与网格共用一套逻辑 |
| 拖动换算：`滚动量 = 拖动量 × 视口高 / 滑块高` | 滑块长度占轨道的比例就是"视口占内容的比例"，代入后正好是"拖一个滑块长 = 滚一屏"。**不需要内容总长的估算值**，因此拖动比例与"滑块看起来多长"的误差无关 |
| 拖动方向的符号**按读者真机手感定**，不要靠推理改 | 现行映射是"**内容跟着手指走**"（手指往下拖，内容也往下走）。我一度按 `LazyListState.scrollBy` 的正负号推理改反了，读者立刻反馈方向反了 |

## 八、搜索与书架：三处"看起来像 bug 的语义问题"

这三条都是**语义**问题，不是崩溃，因此容易被当成"功能没做"而重复实现。

### 1. 搜索必须落在**已生效的筛选之内**

图库的搜索原来走 `mangaRepository.search(query, ...)`，**完全忽略 `sourceFilter`**——
用户在"只看某个图源"（顶栏写着"图库（1 个图源）"）的状态下搜索，会把别的图源的书也搜出来。

- 筛选**下推到 SQL**（`MangaDao.searchInSources`），不要"搜完全库再在内存里过滤"：
  图库是分页读的，内存过滤会让"本页 30 条里只有 2 条属于勾选的图源"变成一页 2 条，
  而 `nextOffset` 按未过滤的总数前进，于是**结果越翻越少、还会漏项**。
- 关键词为空时要退化成"浏览"并**一并带上筛选**，否则清空搜索框会突然把被筛掉的图源放回来。
- 书架的 `pageShelf` 早就把"分类 + 关键词"一起下推了，四种组合都有对应查询，**不用改**。

**验证**（模拟器，4 个图源）：只勾 `/Tachiyomi/local` → 搜 "Microne"（那部漫画在
`/EhViewer/download`）→ 应显示"没有匹配「Microne」的漫画"；再「全选」→ 确认 →
同一关键词立刻搜到那部漫画（并顺带证明"改筛选会用当前关键词重新查询"）。

### 2. 两处搜索框共用 `ui/common/SearchField.kt`

原来是 `OutlinedTextField`，有两个改不动的地方正好是唯二要改的：**形状**是描边圆角矩形
（把顶栏切成一块"表单"），**高度**被 `TextFieldDefaults.MinHeight`（56dp）兜底，
`Modifier.height` 更小会被内部 `defaultMinSize` 顶回去。因此改成 `BasicTextField` 自绘外框：
**胶囊形**（`RoundedCornerShape(percent = 50)`，圆角恒等于高度一半）+ **40dp 高**。

必须保留的约束：**`value` 只由调用方的 `onValueChange` 同步更新**（两页都有防抖，
把防抖后的文本写回 `value` 会复活"每次只能输入一个字符、光标跑到前面"那个坑）。
另外 `onSearch` 刻意可空：传一个空实现会把 IME 搜索键吃掉、键盘不再收起。

### 3. 书架：新加的漫画要立刻出现；刷新键 = 更新章节

**新加的漫画不显示**：书架列表是分页读出来的**快照**，而订阅可见数量的那段代码只处理
**变小**（扫描后陈旧化），变大（新加入收藏）没有任何路径去重读它。补上"变大 → 重建分页会话"。

**刷新键的语义**：它原来调 `scanCoordinator.rescanAll(REFRESH)`，那是"重扫整库目录"，
会把用户没在看的来源也翻一遍。用户要的是**另一件事**：把书架里这些漫画的章节目录重新读一遍。
现在逐个调 `MangaChapterSyncer.sync`（与详情页「更新章节」同一条路径）：

- **范围取"当前筛选下的全部收藏"**（分类 + 关键词），不是已加载的那几页，也不是整库。
  为此加了 `MangaDao.shelfMangaIds(categoryId?, pattern?)`：两个筛选条件都用可空参数
  写在**一条 SQL** 里（`:param IS NULL OR ...`），而不是按组合写四份——四份里任何一份走形
  都会变成"某个组合下更新了不该更新的漫画"，而那种 bug 只在特定组合下出现。
- 给确定进度（第几部 / 共几部）而不是转圈：几十部就是几十秒，没有反馈用户只会以为按钮没反应。
- 列表读取失败的「重试」走**新的 `reload()`**（只重读数据库），不再复用 `onRefresh`。

**验证**（模拟器，书架原有 3 部）：
1. 先看书架（让它的 ViewModel 建立快照 = 3 部）→ 回图库长按加入第 4 部 → 回书架：
   **立刻是 4 部**（同一会话，旧版不会出现）。
2. 点刷新：显示"已更新 4 部漫画的章节"，并且 Manga_C 的卡片从"已发现 1 章，更新中"
   变成"共 2 章"——证明它真的在同步章节目录。
3. 在搜索框输入 "Little"（只剩 1 部）再点刷新：显示"**已更新 1 部漫画的章节**"——
   证明更新范围跟着筛选走。

> 模拟器上这三个操作都是 1 秒内完成的，所以进度条基本看不到；真机书架大时会看到。
> 书架页顶栏是**三个**图标（搜索 / 刷新 / 筛选），别把 x 当成图库的（图库有四个）。

## 十、教训（这一节最值钱）

### 关于验证

1. **"看到现象"不等于"验证了机制"**。我用 `input swipe` 在右侧竖划、看到滑块动了，
   就以为拖动生效——但竖划本来就会滚动列表，滑块动只是"列表滚了"的结果。
   **没有区分"谁在滚"，等于没测。**
2. **验证手势方向要么用只由手势决定的量，要么同时记录两端。** 我用截图量"向下拖 300px
   后滑块的位置"，得出"滑块与手指反向"——但那次**滑块长度从 436px 变成了 226px**
   （网格分页又加载了一批），而"内容变多、位置不变"本身就会让滑块顶端上移，
   **与"反向滚动"产生完全相同的数字**。测量被一个未受控的变量污染了。
   可靠的判据是**放大倍数**（手指位移 199px vs 列表滚动 417.57px，比例 2.098 =
   视口/滑块高，精确吻合；列表自己的手势只会是 1:1）。
3. **不确定就标注不确定**。"模拟器渲染问题是 MuMu 特有"当时是基于语义树与截图矛盾的
   实验，我明确写了"未确认"；后来真机验证确实正常。

### 关于排查

4. **"状态被写坏"比"算法算错"更常见，也更难看出**。跨章那五个坑里有四个是并发写入与
   快照过期造成的，症状全都伪装成"落点算错了"。可复用的判别方法：
   **打印出实际的窗口与项列表**（而不是只看屏幕），一看形状就知道是哪一类。
   我花在推理上的时间远多于加上那两行日志之后花的时间。
5. **不要用"全局记住上一次的值"来去重**。`lastSettledIndex` 那版会把读者**恰好翻到**
   我们曾挪到过的位置也一并丢掉；正确做法是在**能区分来源的那一层**去抑制。
6. **先量规模再判断严重性**。"5356 个章节没有页数"听起来像脏数据，按可用性拆开才发现
   是**可读内容上的 4694 个缺口**，性质完全不同。
7. **改代码前先确认改的是哪一层**。"跨章落点"上我连续改错两次，最终靠**加单测**才发现
   真实结构。
8. **内存总量不能用来归因，必须同时数"事件次数"。** 我在这里栽了一次：只对比
   `dumpsys meminfo` 就断言"native 涨是引擎的固有代价、不是我的回归"，而真相是我的改动
   引入了一个每帧重建环，同一页被 `setImage` 了 111 次。**内存高有两种完全不同的成因**
   （少量页面各占很多 / 同一批页面被反复解码扔掉），总量分不出来，事件计数一眼就能分。
   可复用的做法：在视图的创建/销毁与 `setImage` 上各加一个计数器 + `identityHashCode`，
   先看**同时存活几个**（判断上界有没有守住），再看**总数涨不涨**（判断是不是环）。
   用户用设计口径反问"按预算内存里只该有约 5 页，怎么会 OOM"——**这个反问就是最好的检查**：
   当观测量与设计口径矛盾时，先怀疑自己的实现，而不是给观测量找理由。
9. **"加了新代码才出现"不等于"新代码算错了"**。同一个症状也可能来自新代码**暴露**了
   旧代码里一直存在、只是被另一个写法盖住的结构问题（本例：窗口只增不减时，
   "当前章 ↔ 窗口内容"的循环依赖抖不出来）。因此对照实验只能证明"差异存在"，
   定位仍要回到日志。

### 关于设备操作

10. **`adb exec-out > 文件` 在 PowerShell 里会把二进制改坏**（首字节变成 `EF BF BD`）。
   截图要用设备端存文件再拉：
   ```powershell
   adb -s <serial> shell screencap -p /sdcard/s.png
   adb -s <serial> pull /sdcard/s.png local.png
   ```
11. **取设备数据库的 `exec-out` 路径不稳定**，会静默截断成残片并报
   `database disk image is malformed`。**先校验 `PRAGMA integrity_check`**，
   否则会把坏拷贝当成设备真损坏（我误判过一次）。
12. **在模拟器上造夹具比在真机上试快得多**。`adb push` 放"4 章 × 3 页"这种极端比例，
    比在 90 页的章节里翻到边界快一个数量级，而且能反复重来。
13. **真机地址每次重启都会变**，问用户要当前的 `IP:端口`；装完记得补回
    `MANAGE_EXTERNAL_STORAGE`（重装会重置）。
14. **不要动用户手机里的真实漫画**。所有夹具都是从用户指定的目录**复制**出去的，
    手机上只装 APK、补权限、截图。

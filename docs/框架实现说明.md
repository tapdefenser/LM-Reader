本文是 [开发文档](./开发文档.md) 的实施补充，只描述**代码契约**：模块边界、类型签名、扫描算法、数据库表与 UI 契约。产品需求、交互细节与验收标准以开发文档为准，本文不重复也不覆盖它。

**实现完成后的修订（v0.1 → v0.2）**：v0.1 是在写代码前冻结的契约；真机联调后有三处必须改，已同步回本文。原因与排障过程见 [协作记录](./多agent协作交流文档.md) 的"本轮发现并修复的问题"。

| 编号 | v0.1 写法 | 实际实现 | 原因 |
|---|---|---|---|
| R1 | `ScanResult` 等类型放在 `core:index`（§4.1），而 §3.6 的仓储需要它们、§1 又禁止 `core:model → core:index` | 实体放 `core:model`，`core:index` 用 `typealias` 重导出 | 原写法与依赖方向不可同时满足；两个全限定名都能解析，调用方无需改动 |
| R2 | `ContentTree.openChild(documentId: String)`（§3.3） | `openChild(child: ChildNode)` | 子项名称已由 `listChildren` 拿到；只传 ID 会迫使实现回查提供方，每个目录多一次 binder 查询 |
| R3 | `StructureScanner.scan(request, root, events)`（§4.2） | `scan(request, root, factory = …, events)` | 扫描器实例被多来源复用，不能持有某一个来源的工厂。v0.1 把工厂固定在构造函数里，于是"调用方忘了传真实工厂"时每个子目录都打不开**却不抛异常**——真机实测现象是"根目录列出 65 个子项、65 个失败路径、0 部漫画"。现在占位实现直接抛异常，同类接线错误立刻可见 |

## 1. 模块与依赖方向

```text
:app            Android 宿主：Compose 导航、主题、DataStore、SAF 选择器、依赖装配
 ├─ :core:storage   SAF/归档/PDF 访问、扫描调度、扫描落库
 ├─ :core:database  Room 实体、DAO、迁移
 ├─ :core:index     纯 Kotlin 结构扫描算法、自然序比较、ComicInfo 解析
 └─ :core:model     纯 Kotlin 领域类型、稳定 ID、仓储契约（无 Android、无网络）

依赖只允许自上而下：app → storage/database/index → model。
core:model 与 core:index 是纯 JVM 模块，禁止 import androidx.* / android.*。
```

禁止反向依赖与循环依赖。`core:index` 不认识 Room、SAF 或 Compose；`core:database` 不认识 SAF 与 Compose。

## 2. 编码与命名约定

### 3.2 身份

```kotlin
/**
 * 稳定 ID：由 SAF 文档 ID 与来源种类派生，不使用列表位置、可改标题或绝对路径
 * （开发文档 15.3「身份」）。同一 documentId 在两个表里得到不同 ID。

```

实现要求：`SHA-256(documentId + '\u0000' + kind.name)` 取前 32 个十六进制字符，前缀 `m_`/`c_`/`s_`。同一输入必须永远得到同一输出（跨进程、跨重装可重算）。

### 4.3 算法（必须逐条实现）

术语：`container` 指可继续展开的目录；`leafChapter(d)` 指 `d` 的**直接子项中至少有一张受支持图片，且没有子目录、也没有 CBZ/ZIP/PDF**（开发文档 5.1）。判定顺序必须是「先确认没有子目录，再确认有图片」，因为先看到图片不能断言没有子目录。含归档文件的目录不是叶子：`漫画名/cover.jpg` + `漫画名/第1话.zip` 这种"章节就是压缩包"的文件夹必须被当成**一部漫画**（章节是那些压缩包），否则它的父目录会被判成漫画并跳过其余子文件夹（真机 `/Tachiyomi/local` 51 个子文件夹只扫出 1 张卡片的原因）。

**两种解释共用一次遍历（2026-09-25 已落地）**：一个目录的直接章节 = 「它直接含的 CBZ/ZIP/PDF」∪「它直接子目录里的叶子图片目录」。`ScanRequest.sourceKind` 因此**不再决定扫描行为**，只参与卡片身份（`mangaId`）；界面只剩一张路径表，"同一目录要加两遍"这件事消失。

**多章节**（`LayoutMode.MULTI_CHAPTER`，两种 `sourceKind` 同构）：

```text
scanManga(d, depth):
  children = d.listChildren()
  if children has image and children has directory:
     Diagnostic("目录同时包含图片和子目录，未按叶子章节处理")
  archives = children where isArchiveFile()      // 零额外 IO：子项列表已经在手
  if archives.isNotEmpty():                      // 第一条规则：直接含归档 -> 这就是一部漫画
     emit Manga(anchor = d, chapters = [自然序第一个归档])   // 章节标题 = 去扩展名的文件名
     return                                      // 找到一个章节就够：其余子项全部跳过（用户要求）
  for child in children where child.isDirectory, 按自然序:
     if isLeafChapter(child):                    // 第二条规则：找到第一个叶子图片目录
        emit Manga(anchor = d, chapters = [child])           // 章节标题 = 目录名
        return                                   // 其余子文件夹全部跳过
  if depth == 0 and children has directory == false:
     if children has image: Diagnostic("根目录自身是叶子图片目录，按根特例…"); emit Manga(anchor = d, chapters = [d])
     else: Diagnostic("目录内没有受支持的图片，也没有 CBZ/ZIP/PDF")
     return
  if recursive or depth == 0:
     for child in children where child.isDirectory:
        scanManga(child, depth + 1)
```

**单章节**（`LayoutMode.SINGLE_CHAPTER`，两种 `sourceKind` 同构）：

```text
scanSingle(d, isRoot):
  children = d.listChildren()
  for file in children where isArchiveFile():
     emit Manga(anchor = file, chapters = [file])   // 每个归档文件自身一本共 1 章
  if children has no directory:
     if children has image and children has no archive:
        emit Manga(anchor = d, chapters = [d])      // 叶子图片目录一本共 1 章（根自身即"根特例"）
     else if isRoot and children has no image and children has no archive:
        Diagnostic("目录内没有受支持的图片，也没有 CBZ/ZIP/PDF")
     return
  // 有子目录：本身不是章节，也不因为"有图片"就变成章节
  if children has image:
     Diagnostic("目录同时包含图片和子目录，未按叶子章节处理")   // 混放，不静默也不自动当章节
  if recursive or isRoot:
     for child in children where child.isDirectory:
        scanSingle(child, isRoot = false)
```

**章节种类**：叶子图片目录 → `ChapterKind.IMAGE_DIRECTORY`，归档文件 → `ChapterKind.ARCHIVE`；`chapterId` 由 `(documentId, ChapterKind)` 派生，因此同一个物理路径的两种解释不会撞 ID。

**递归开关的精确含义**（开发文档 1.3 / 5.1）：`recursive = false` 时只把**根自身及根的直接子目录**当作漫画候选，但为了识别多章节候选，允许读取候选的直接子目录层（即 `isLeafChapter` 检查）——这种必要的结构检查不算“向更深处发现漫画”。

**停止条件**：一旦某目录被判定为漫画锚点，其已归属章节目录不再作为独立漫画继续递归；但它的**其他**直接子目录仍要按递归开关继续检查（开发文档 5.1「仍须检查其其他直接子目录」）。

**排序**：章节顺序按 `NaturalOrder.compare(title)`；漫画名称排序由数据库负责，扫描器只保证给出 `sortKey`。

**生成器与根 documentId**：`generation` 由调用方传入（`System.currentTimeMillis()` 或自增）。根自身的章节用 `rootDocumentId` 作为 chapter `documentId`。

### 4.4A 章节顺序（`ChapterOrdering`）

### 4.5 ComicInfo 解析

```kotlin
/**

 * 解析必须关闭外部实体与网络访问，并限制大小（默认 2 MiB）。

object ComicInfoParser {
    const val MAX_BYTES: Long = 2L * 1024 * 1024

    fun parse(ownerId: String, ownerType: MetadataOwnerType, xml: String, sourceLabel: String): MetadataRecord

    /** ComicInfo.xml 判定不区分大小写，但不把任意 XML 都当 ComicInfo。 */

/** 简介摘要：Summary 优先，缺失时按上游字段组织，最后才压缩 XML 文本，最多 [MAX_SUMMARY_LENGTH] 字符。 */
object SummaryBuilder {
    const val MAX_SUMMARY_LENGTH = 400

    /** excludeName：与 Series 相同时不重复一行「名称」（EhViewer 的 Series 就是目录名的后缀部分）。 */
    fun build(record: MetadataRecord, excludeName: String? = null): String?
}

/**
 * 两侧上游 ComicInfo 的字段语义映射（开发文档 7.1A）。
 * 判据看字段集合（两侧互斥的那几个字段），不看命名空间前缀。
 */
object ComicInfoFields {
    enum class Flavor { TACHIYOMI, EHVIEWER, UNKNOWN }

    fun flavor(fields: Map<String, String>): Flavor

    /** Mihon 取 Writer、EhViewer 取 Penciller（画师），另一侧作回退。 */
    fun author(fields: Map<String, String>): String?

    /** EhViewer 的 Writer 是社团；Mihon 语义下等同作者，不重复展示。 */
    fun group(fields: Map<String, String>): String?

    /** Summary 缺失时的结构化简介；一个可用字段都没有时返回 null。 */
    fun describe(fields: Map<String, String>, excludeName: String? = null): String?

```

字段映射（两侧上游兼容）：`Series, Title, Writer, Penciller, Summary, AlternateSeries, Characters, Teams, CommunityRating, Genre, Web, PageCount, LanguageISO, Number, Volume`。EhViewer 的 `AlternateSeries/Characters/Teams/CommunityRating` 与 Mihon 的命名空间扩展字段都必须保留在 `fields` 中，键用本地名。**同名字段的业务含义不等同**，作者一类的派生值必须走 `ComicInfoFields`。

`normalizedSearchText` = 规范化（NFC、小写、去多余空白）后的「名称 + 别名 + 全部字段值 + XML 文本节点」，用于开发文档 6.4 的搜索。

**解析器的平台差异（真机教训）**：`secureDocumentBuilder()` 是「标准加固试一次、被拒退回最小配置」；Android 的 libcore/Harmony 实现不认 OWASP 那套属性，并会在 `newDocumentBuilder()` 抛 `ParserConfigurationException: This parser does not support specification "Unknown" version "0.0"`。XXE 的保证改由「解析前按原文拒绝 `<!DOCTYPE`」+「空 EntityResolver」+「2 MiB 上限」承担。

**补全阶段的读取路径（真机教训）**：`MetadataBackfillWorker` 只通过注入的 `openTree`/`openInputStream` 取目录与流（生产装配来自 `TreeAccess`），**不得**直接拼 `DocumentsContract` URI——在「全部文件访问」下 documentId 是绝对路径，与提供方要的 `primary:…` 不匹配，会让每一部漫画都被判成“没有 XML”。

### 5.0 章节顺序与已读标记（v6，2026-09-28）

### 5.0.1 翻译数据与页面（v7，阶段 2）

### 6.3 元数据补全（封面**不在**这里）

```kotlin
/**
 * 补全阶段（开发文档 6.1 第 2 步）：为已发现漫画补首章 ComicInfo。
 * 低优先级，阅读优先；失败只影响该卡片，不阻断扫描。
 */
class MetadataBackfillWorker(
    /** 生产装配传 treeAccess；测试传内存目录树与字节流。 */
    private val openTree: (treeUri: String, documentId: String) -> ContentTree?,
    private val openInputStream: (treeUri: String, documentId: String) -> InputStream?,
    private val mangaRepository: MangaRepository,
) {
    constructor(treeAccess: TreeAccess, mangaRepository: MangaRepository, clock: () -> Long = ...)

    suspend fun backfill(mangaIds: List<String>)
}
```

**读目录必须走 `TreeAccess`（2026-09-28 真机教训）**：这里原本直接用
`DocumentsContract.buildChildDocumentsUriUsingTree(treeUri, documentId)` 拼 SAF URI。
在「全部文件访问」下 `documentId` 是**绝对路径**（`/storage/emulated/0/…`），而
ExternalStorageProvider 的 documentId 是 `primary:…`，拼出来的 URI 查不到任何子项，
于是**每一部漫画**都走"没有 XML"分支：`hasMetadata` 永远是 0、简介与作者永远是空。
模拟器实测同一目录：`primary%3A…` 那条返回 17 行（含 `ComicInfo.xml`），
`%2Fstorage%2F…` 那条返回 `No result found.`。
现在只通过注入的两个函数取树与流（与 `CoverResolver` 同一形状），
documentId 的口径由 `TreeAccess` 统一，纯 JVM 测试也能覆盖"首章有/没有 XML、顶层兜底、
目录读不到"这些分支。

**v4→v5 迁移**把被这个缺陷误标成"已探测"的行（`hasMetadata = 0`）退回
`metadataProbedAt = NULL` 重新读一遍：补全队列要求 `metadataProbedAt IS NULL`，
而重扫会保留已有值，不修这一列的话修好代码也永远轮不到它们。


**封面已从这里搬走（用户口径：扫描只写路径）。** 原先封面由补全阶段取，代价是
"每部漫画多开一次章节目录"（扫描变慢）加上"每轮只补 120 条"（几千条待补要刷十几次
图库才轮到，真机上 5408 部只有 742 部有封面 = 图库几乎全是破图）。

现在封面走**图库/书架滚动时的懒加载**：

- `core:storage` 的 `CoverResolver`：多章节取自然序第一章的第一页（前 3 章内找图片
  目录），单章节取锚点目录本身的第一页；目录打不开/确实没有首图 → 返回 null；
- `app` 的 `CoverProbeQueue`：列表把**当前可见**的卡片下标上报，队列按批（30）取、
  并发 2、上限 200 条待办（猛划时丢最旧的）；
- 探测结果写进 `mangas.coverProbedAt`（成功与失败都写）：**取过一次就不再取第二次**，
  只有详情页的「更新章节」会强制重取；
- **更新封面的地方同时更新简介**（用户要求，2026-09-28）：三处落库
  （图库滚动、书架滚动、详情页）都走 `core:storage` 的 `CoverMetadataWriter`，
  它先写 `markCoverProbed` 再调 `MetadataBackfillWorker.backfillOne` ——
  封面与简介读的是**同一批目录**，分开走的结果是"卡片有封面、简介一直是空的"。
  三个调用点共用一个函数，避免再出现"图库有简介、详情页没有"这类分叉；
- 简介（ComicInfo）**仍然**有扫描期补全，队列看 `metadataProbedAt`：没有这一列时
  "读不到 XML"的条目会永久占据队头，每轮扫描重开同一批目录（真机上 5408 部全是
  `hasMetadata = 0`，也就是队列从来不前进）。`backfillOne(force = false)` 也按这一列
  自我守卫，所以滚动懒加载不会把已经读过目录的作品重复枚举；详情页的
  「更新章节」传 `force = true`。

### 6.3A 单漫画章节同步（P2.0）

详情页的「更新章节」与整库的快速发现分开：快速发现只需找到一章就可以先显示卡片，单漫画同步则必须完整枚举锚点目录的直接章节。

- 多章节漫画的章节集合 = 锚点目录的直接 CBZ/ZIP/PDF 文件 + 直接子目录中的叶子图片目录；自然序排列。
- 单章节漫画在发现时已经精确，同步可直接返回现有章节。
- 只有锚点及所有候选子目录都成功枚举时，才设置 `fullyEnumeratedContainers = setOf(anchorDocumentId)` 并允许删除已消失的章节。
- 任一目录无法打开、IO 失败、授权丢失或任务取消时，整次结果不落库，原章节和阅读进度保留。
- 落库继续携带 `sourceRevision`；`ScanPersistReport.accepted = false` 表示同步期间来源配置已变，UI 应提示重试而不得显示成功。
- **「更新章节」成功后必须重取封面**（用户要求"更新章节必拿"）：此刻的章节清单才是完整的，
  "第一章"是权威的。封面路径交给引擎时用 `file://`（直接文件访问下）或
  `content://`（SAF），**不生成缩略图文件**；`coverDocumentId` 必须能直接构造出可读 URI。

### 6.5 章节页源与阅读进度（P2.1）

```kotlin
data class ReaderPage(
    val pageId: String,
    val ordinal: Int,
    val displayName: String,
    val documentId: String,
)

interface PageSource {
    suspend fun pages(): List<ReaderPage>
    suspend fun open(page: ReaderPage): InputStream
}
```

- 图片目录章节只枚举直接受支持图片，按 `NaturalOrder` 排序；页 ID 由 `chapterId + documentId` 稳定派生。
- `PageSource.open` 每次返回新的可关闭流，解码方不得把整章字节一次装入内存。
- 列页成功后回填章节 `pageCount` 和首页封面；失败不伪造页数。
- 阅读位置写入现有 `reading_progress`表：漫画、章节、页序号和条漫页内比例；重扫不删该表。
- P2.1 首切片只开放图片目录章节。归档/PDF 经同一工厂返回结构化「尚未支持」，UI 不启动假阅读器。

**页内比例的实际决定（P2.2，参照 Mihon 后收窄）**：Mihon 的分页与条漫阅读器都**只持久化页码**（`last_page_read = page.index`，0 基），恢复时 `scrollToPositionWithOffset(page, 0)`，页内偏移设计上丢弃。本项目决定同样只存页码，`reading_progress.intraPageRatio` 继续保留在表里但恒为 0，供将来单独评估。因此开发文档 12 节「条漫保留页内比例进度」这一条**本轮不实现**，改动需另开切片并单独验证恢复精度。

**大图内存策略（参照 Mihon 后修正）**：Mihon 的阅读路径**不使用** `BitmapRegionDecoder` 或区域解码——`WebtoonSubsamplingImageView` 整个类只有一个返回 `false` 的 `onTouchEvent`。它对超长图的真正手段是**下载期切图**（`split_tall_images`，`h > w*3` 时按 `max(屏宽,屏高)*2` 切块并重编码），阅读器只负责把整页解码成一个 bitmap（Coil，按视图尺寸采样）。本项目没有下载阶段（只读本地源），因此超长图的内存保护必须自己做：阅读器按视口高度采样解码，并在超大图上做尺寸预算，不能照搬 Mihon 的"下载期已切好"这一前提。

### 7.1 导航

```text
route "onboarding"   -> GalleryPathScreen(isOnboarding = true)     首启入口
route "library"      -> LibraryScreen                              首次点“下一步”后进入
route "bookshelf"    -> BookshelfScreen                            后续冷启动默认

```

启动决策（开发文档 1.3「首启与后续启动」+ 第 3 节）：读 `onboardingCompleted`，false → 首次进入 `onboarding`；true → `bookshelf`。

主菜单五项：图库 / 书架 / 翻译队列 / 导出队列 / 设置。本步翻译队列与导出队列**可以进入但只显示“未实现（P3/P4）”说明页**，不得显示假进度或空壳控件（开发文档 17 完成标准：不存在仅摆放未接线的核心控件）。

### 7.2 图库路径配置页（本步重点）

结构（开发文档 4.1，2026-09-25 由两张表合并为一张）：

- 顶部说明（仅引导态）+ **一张路径表** + 底部固定操作条。
- 只有一张表「图库路径列表」：一次扫描同时识别图片章节与归档章节，来源的 `kind` 只作身份用。
- 固定表头四列：`路径 | 子目录 | 类型 | 删除`（用户原文第四项是类型、第二项是删除；表头顺序按用户原文为「路径、删除、子目录、类型」，实现按可读性排列为「路径、子目录、类型、删除」并在 KDoc 说明差异，不得改变四列的语义）。
- 表独立竖向滚动区域；行内路径可折两行，但保留四列。
- `+`：`ActivityResultContracts.OpenDocumentTree` → 取持久权限 → 立即加入并扫描（唯一的添加入口，不再需要选择"加到哪张表"）。
- 行编辑：点子目录复选框或**类型下拉**即改动即保存；点路径打开改名/重新选择目录的弹窗。
  类型下拉的选项**由 `LayoutMode.entries` 生成**，文案取自 `ui/common/LayoutModeLabels.kt`
  （穷尽 `when`，新增枚举值会编译报错提醒补文案）——用户已预告将来要加「混合」，
  因此这里的选项列表不写死为两个。
- 删除 `×`：移除来源并提供短时撤销（Snackbar）。**不删源文件、书架、译文**；该来源的卡片标成陈旧并隐藏。
- 拖动排序：长按手柄上下拖动，松手立即持久化；另提供上移/下移辅助操作（无障碍）。
- 底部「强制重新扫描索引」：无保存路径时禁用；执行中显示进度与取消。
- 底部「下一步」（引导态）/「完成」（设置态）：至少一个已保存且可读路径才能进入图库；不等待扫描完成。

### 7.3 图库页

- 顶栏：菜单、搜索框、刷新按钮、显示方式切换。
- 列表按 40 项增长（开发文档 6.4）：首屏加载 40；滚动到末端追加 40；扫描继续时若当前额度未满则自动补入。
- 卡片：封面、名称、简介预览（最多两行）、章节状态（`chapterCountKnown = false` 显示「已发现 N 章，更新中」）、书架标记、「图片/归档」来源徽标。
- 扫描条：显示「已发现 N 项」与各源状态，**不显示伪造百分比**。
- 空态 / 错误态 / 部分失败态都必须有可操作文案（开发文档 3）。

### 7.4 书架页

- 默认所有收藏；右上分类按钮打开右侧分类栏：全部 / 未分类 / 自建分类（带数量）。
- 新分类 `+`：名称必填 1–40 字符，同名禁止。
- 分类长按：重命名与文风、上移、下移、删除；删除确认后收藏移到未分类。
- 卡片长按进入选择态可批量移出书架（第一步只需移出，批量翻译/导出留 P3）。
- 空态文案说明如何加入书架。

### 7.4A 漫画详情页（P2.0）

- 显示真实封面、标题、作者、简介、来源路径和自然序章节列表；不伪造页数或阅读进度。
- `chapterCountKnown = false` 时明确显示「已发现 N 章，点击更新章节」；同步成功后才显示「共 N 章」。
- 加入书架时从已有分类中选择；移出书架不删漫画、章节或文件。
- 阅读器尚未接线时不显示可点击的假「开始阅读」按钮；阅读入口随下一切片接入。

### 7.5 状态与错误

每个页面必须有 `Loading / Empty / Error(reason, action) / Content` 四态。错误文案必须可操作：例如「目录授权失效—重新授权」「未选择任何图库路径—去设置」。不得用空列表代替错误。

### 7.6 基础阅读器（P2.1）

- 详情页「阅读/继续阅读」恢复上次章节和页；点章节行从该章第一页开始。
- 分页模式默认右到左，显示页码、滑块、上/下一章；页变更即保存可恢复位置。
- 单击页面显隐顶栏与底栏；图片解码根据屏幕尺寸采样，不预解码整章。
- 来源失效、空章或不支持的章节类型显示可返回的明确错误，不闪退。

## 9. 已知限制（第一步明确不做，且不得在 UI 上假装已做）

1. **搜索**：本步只支持名称与 `normalizedSearchText` 的 `LIKE` 匹配，且不做 2-gram 侧表；万级库的搜索性能未验证。UI 必须显示「正在更新索引，结果可能不全」而不是最终否定结论。
2. **分页**：使用 `LIMIT/OFFSET`，非开发文档 6.4 的会话顺序表；扫描中新增条目可能造成翻页重复，UI 用 `(mangaId)` 去重。
3. **缩略图**：不生成缩略图缓存，直接解码原图并限制采样；LRU 上限为 P1。
4. **归档与 PDF**：P2.1 已建立统一 `PageSource` 契约并实现图片目录阅读；归档/PDF 页清单与渲染仍待后续适配。
5. **目录快照**：只记录「容器是否完整枚举」的摘要，不做逐成员对账的完整实现。
6. **翻译/导出/阅读器**：翻译与导出仍未实现；阅读器 P2.1 仅完成图片目录的基础分页与进度恢复，条漫和高级设置待后续切片。
7. **备份恢复**：不在本步。

以上每一项都必须在实现处写 KDoc 标注 `限制（开发文档 X.Y 的 P1 项）`，便于后续替换时定位。

# OCR 硬件加速

在「设置 → API 与翻译引擎 → OCR 配置 → 本地 OCR 配置」选择加速方式。

| 选择 | 尝试顺序 |
| --- | --- |
| 自动 | QNN → NNAPI → CPU |
| QNN（高通） | QNN NPU → QNN GPU → CPU |
| NNAPI（系统） | NNAPI GPU/NPU → CPU |
| CPU | ONNX Runtime CPU |

指定 QNN 或 NNAPI 时，不会切换到另一种加速方法。驱动不可用、模型初始化或推理失败、实际没有运算进入硬件后端时，自动回退到 CPU。检测与不同语言的识别模型分别选择、验证后端，所以实际后端可能不同。

页面显示用户选择和实际后端。首次硬件推理会检查 ONNX Runtime 的执行记录；注册了后端但所有运算仍在 CPU 上的情况不能显示为成功加速。首次使用需要编译模型，时间长于后续推理。已加载模型保持当前配置；修改选择后通过「全部暂停并卸载」释放模型，下次识别使用新选择。

QNN 使用官方 ARM64 插件和运行库，并通过手机公开的 FastRPC 接口访问高通硬件。NNAPI 保留系统驱动枚举和 `CPU_DISABLED` 选项，联发科、麒麟等设备可使用系统开放的 GPU/NPU 驱动；具体支持情况由系统驱动和模型运算决定。Android 8.0 或没有兼容驱动的设备继续使用 CPU。

硬件会话把检测输入固定为 `1×3×960×960`、识别输入固定为 `1×3×48×320`，以满足固定形状要求。超出识别宽度的文字行使用动态宽度 CPU 会话，保持原分辨率与内容。不改变上游模型权重或字符字典。

旧版硬件加速开关开启时迁移为「自动」，关闭时迁移为「CPU」。新选择通过 `vision_ocr_backend` 保存并包含在设置备份中；仍兼容旧版备份的布尔设置。

## 2026-10-01 真机验证

小米 14 Ultra（SM8650，Android 16）没有通过 NNAPI 提供 GPU/NPU 设备；QNN 的检测、中日与拉丁文字识别、韩文识别模型都产生了真实 NPU 执行记录。

5 项手机测试通过：后端执行验证、中日英韩文本与 CPU 对比、超长文字行、卸载重载、显式后端选择，以及 SEG GPU 与 OCR NPU 同时运行。另有 2 项 x86_64 模拟器测试验证无硬件驱动时的回退和执行记录判定。

同一张内存绘制的英文 `HELLO` 图片，模型预热后 5 次完整 OCR：

| 后端 | 耗时（毫秒） | 中位数 |
| --- | --- | --- |
| CPU | 832、985、833、861、953 | 861 ms |
| QNN NPU | 228、270、253、265、253 | 253 ms |

该样例约快 3.4 倍，包含图片预处理、检测与识别；不同漫画、文字行长度和系统负载会改变耗时。这不是联发科或麒麟设备的实测结果。

依赖固定为 ONNX Runtime Android 1.28.0、QNN 插件 2.6.0、QNN Runtime 2.50.0。插件和运行库使用不同许可证，原文随 APK 保留在 `vision/notices` 下。QNN 增加原生库体积，并需要解压原生库供 DSP 加载。

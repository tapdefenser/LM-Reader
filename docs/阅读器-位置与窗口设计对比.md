# 阅读器位置与窗口：两种实现的对比分析

> 这份文档回答一个问题：**"大表（已加载章的全部页路径，只增不减）+ 小表（真正的解码缓冲）+ 双向按需拉章"**
> 与**当前实现（滑动窗口 + 拍平项列表 + 下标位置）**哪一种更好，各自会出什么问题。
>
> 结论先放这里：**两者都是在"位置用下标表达"这个前提下做的局部折中**；
> 真正决定正确性的是"位置用**身份（key）**表达还是用**下标**表达"。
> 采用身份 + 有界窗口 + 显式对账，可以同时避开两边的问题。

---

## 0. 一个关键观察：整套系统本来只有位置这一处不是按身份记账的

| 层 | 用什么记账 | 会不会因重排而错 |
|---|---|---|
| 磁盘预取缓存 `PagePrefetcher` | 文件名 = `范围哈希 + pageId` | 不会（键是身份） |
| 项列表 `ReaderItem.key` | `pageId` / `transition:from->to` | 不会（键是身份） |
| 分页器 `key = { items[it].key }` | 同上 | 不会（Compose 与它同向） |
| 引擎视图 `EnginePageView` | `remember(page.pageId)` + tag | 不会（键是身份） |
| 章节加载 `loaded[chapterId]` | `chapterId` | 不会（键是身份） |
| **读者位置 `currentPageIndex`** | **`items` 里的下标** | **会——四个 bug 全出在这里** |

也就是说：**Compose 的懒布局本身就是按 key 记账的**（`LazyLayoutItemProvider` 维护 key→index 映射，
列表变化时会尝试把锚点项保持在原位）。我们的状态却用下标记位置，于是每次重排都要
"事后翻译一次"（`reanchorIndex`），再靠启发式（`suppressSettleFrom` / `cameFromScrollIntoView`）
把分页器的回报和这次翻译对上。**bug 就活在这层翻译里。**

## 1. 两种实现写清楚

### 1.1 实现 A：滑动窗口 + 下标位置（当前）

```
chapterList : List<ChapterRecord>          // 目录（DB）
loaded      : Map<chapterId, ViewerChapter> // 已枚举页清单的章【只增不减】
window      : List<ViewerChapter>           // = 规划范围 ∩ loaded【滑动，会放掉已加载的章】
items       : List<ReaderItem>              // window 拍平 + 过渡项【每次 window 变就重建】
currentPageIndex : Int                      // 位置 = items 的下标【会随重排平移】
```

不变量（必须靠代码维持）：
1. `items` 与 `window` 严格一致；
2. 任何重排后 `currentPageIndex` 必须按项身份重算（`reanchorIndex`）；
3. 分页器的数字位置与状态机的下标必须对账（`positionKey` + 抑制标志）；
4. 窗口必须含当前章 ±1（否则过渡项缺失、跨章卡死）；
5. 窗口等价时不能换 `items` 实例（否则分页器白重排、右到左模式下抖一格）。

### 1.2 实现 B：大表只增不减 + 下标位置（你的模型）

```
chapterList : List<ChapterRecord>
loaded      : Map<chapterId, ViewerChapter> // 只增不减
items       : List<ReaderItem>              // 所有已加载章的页 + 过渡项【只追加，不重编号】
currentPageIndex : Int                      // 位置 = 下标【前进路径上不再平移】
```

不变量（少得多）：
1. `items` 只追加（可在末尾追加整章）；
2. 前进阅读时**已存在项的下标不变**。

### 1.3 实现 C：身份位置 + 有界窗口（建议形态）

```
positionKey : String                        // 位置 = 项身份（pageId / transition:from->to）
items       : List<ReaderItem>              // 有界窗口（可按需淘汰远离当前章的章）
currentIndex: Int                           // = items.indexOfKey(positionKey)【派生量，随时重算】
```

不变量：
1. 位置只有唯一真相：`positionKey`；
2. `currentIndex` 永远是**派生**的，任何重排后重算，不存在"过期下标"这个概念；
3. 淘汰只能淘汰"远离当前章的章"，且淘汰后身份仍可解析（见 §4.3）。

## 2. 逐项对比

| 维度 | A 滑动窗口 + 下标 | B 只增大表 + 下标 | C 身份 + 有界窗口 |
|---|---|---|---|
| **位置稳定性（前进）** | 差：每章可能平移 4 项（3 页 + 1 过渡） | **好**：只追加，不重编号 | **好**：下标是派生的，平移无意义 |
| **位置稳定性（后退/插入）** | 差 | **仍差**：更早的章加载完成会插在当前项之前 | 好 |
| **内存上界（items）** | 名义有界（≈预载范围） | 无界 | 有界（可调） |
| **内存上界（loaded）** | **实际无界**（从不清） | 无界 | 有界（需加，见 §4.4） |
| **每次重排的开销** | 小（几十项） | **大**：O(全表) 重建 + 分配 | 中（可加哈希索引，O(1) 查位） |
| **不变量个数 / 静默出错风险** | 5 条 → 高 | 2 条 → 低 | 3 条 → 低 |
| **与 Compose 的方向** | 逆向（框架按 key，我们按下标，需对账） | 逆向（同上，只是少触发） | **同向**（都是 key） |
| **失败模式可观测性** | 静默错页（最难查） | 内存增长（可见） | 几乎不存在静默错页 |
| **改动成本** | 已实现 | 中（撤掉窗口淘汰） | 中（换位置语义 + 对账） |

## 3. 各自的问题清单（具体、带数字）

### 3.1 实现 A 的问题

1. **位置漂移（已发生）**：窗口前端放掉一章 = 3 页 + 1 过渡 = **4 项**，下标整体平移 4。
   已由单测钉住：`窗口前端放掉一章会让项下标整体平移 4 格`（12→8，过渡项 11→7）。
   分页器停在旧数字上就正好偏 4 格，即用户报的"从第 5 页开始 / 跳回上一章首页 /
   又出现一张过渡页 / 1 页的章被漏掉"。
2. **正反馈环（已发生）**：窗口内容依赖当前章，而当前章从落页下标反推 →
   "章翻转 → 窗口重算 → 表长变 → 分页器抖一格 → 章再翻转"，每帧一轮，
   实测每秒重建 80 多个引擎视图、`setImage` 111 次/页，native 顶到 300MB。
3. **`reanchorIndex` 的静默兜底**：锚点项不在新列表里时它保留**旧下标**（`coerceIn`），
   于是静默落到另一页——最坏的一类失败：不报错、只是位置错了。
4. **`loaded` 其实没有上界**：我的窗口有界化只让 `items` 变短，`loaded` 从不清。
   所以"省内存"这个理由**基本不成立**（见 §4.4 的量化）。
5. 额外的三处耦合：`writeItems` 的窗口等价判断、`nearWindowEdge`、`chapterChanged` 门控——
   都是为了兜住 (1)(2) 而存在，本身又是新的出错面。

### 3.2 实现 B 的问题

1. **它并没有消灭"插入在当前项之前"这一类平移**。列出页是异步的：
   早于当前章的章（预载的"往前"那几章）如果在读者已经前进之后才加载完，
   它会被插进 `items` 的前部 → 下标整体变大 → 与 A 同类的错位（只是频率低得多）。
   所以 B 仍然需要"身份位置"或对账机制，**单靠只增不减并不够**。
2. **无界增长**：`items` 与 `loaded` 都随阅读增长。按 `ReaderPage`（4 字段、其中
   `documentId` 是 SAF 长 URI，实测量级 150–300 B/页）估算：

   | 规模 | 页数 | `loaded` 元数据 | `items` 每次重排的分配 |
   |---|---|---|---|
   | 100 章 × 20 页 | 2,000 | ~0.5 MB | ~64 KB |
   | 1,000 章 × 30 页 | 30,000 | ~7.5 MB | ~1 MB |
   | 5,000 章 × 50 页 | 250,000 | ~60 MB | ~8 MB |

   前两行完全可接受，第三行（超大合集）每次换章都要重建 25 万项列表 = 可见卡顿 + GC 压力。
3. **"循环队列"在这里不适用**：视觉列表必须是**线性有序**的，
   LazyList/Pager 需要 `index → item` 的直接映射。真做成环形缓冲，
   就要多一层"环位置 → 线性下标"的翻译，而那正是 A 出错的那层翻译。**环形适合小表，不适合大表。**
4. **跳章时**要么保留一张巨大的表，要么重置它——重置就是一次平移（仍需 C 的对账）。
5. 配套逻辑要重构：现在"窗口"同时承担"显示什么"和"该加载什么"两个职责；
   只增大表之后两者必须拆开（显示=全表，加载=规划），否则 `nearWindowEdge` 失去意义。

## 4. 结论与建议形态

### 4.1 结论

**在"位置用下标"这个前提下，A 和 B 的差别只是"多久错一次"：A 每章都可能错，B 偶尔错。
真正的分界是位置语义。**

- A 的失败模式是**静默错页**（最难查、用户直接可见）；
- B 的失败模式是**内存/卡顿**（可见、可度量、可加限流）；
- C 把两者都消除：位置是身份 → 平移不再是问题 → 窗口可以有界 → 内存也可控。

所以：**不要把 A 改成 B（那只是把高频错误换成低频错误 + 无界内存），
而是把位置从下标改成身份，然后窗口的取舍就变成纯粹的内存问题（可以随便调）。**

### 4.2 落地步骤（建议顺序）

1. **位置改身份**：`ReaderUiState.positionKey` 取代 `currentPageIndex` 作为真相；
   `currentIndex` 变成派生属性（`items.indexOfKey(positionKey)`）。
   `ReaderItem.key` 已经存在且稳定，改动是局部的。
2. **对账改成"派生 + 无条件归位"**：分页器的同步 effect 以
   `(positionKey, items.size)` 为 key，滚动中也强制定位（`requestScrollToPage`），
   并在分页器确认到达之前把它的回报当回声丢掉（判据是**期望身份**，不是下标）。
3. **窗口改回"尽量只增"**：前进路径零重编号；只在读者跳到远处、或与当前章距离超过上限时
   才淘汰（淘汰本身安全，因为位置是身份）。
4. **给 `loaded` 加上限**（当前完全没有）：只保留当前章 ±N 章，N 取 20 就够——
   按 300 B/页、每章 30 页算，上限约 180 KB。**这是"大表只增不减"唯一真正需要补的地方。**
5. **淘汰规则**：永不清除当前章及其相邻章；被淘汰章的身份若恰好是 `positionKey`
   （理论上不可能，因为当前章永不被淘汰），退化为"该章第一页"。

### 4.3 身份消失时怎么办

`positionKey` 是 `pageId` 或 `transition:from->to`。淘汰永远不动当前章与相邻章，
因此当前身份**不会消失**。真正可能消失的是"当前项是过渡项、而它的 `from` 章被淘汰"——
按 §4.2 第 5 条，过渡项两侧的章都属于"相邻章"，同样不会被淘汰。这条要在代码里写成断言，
而不是靠"应该不会"。

### 4.4 顺带纠正我之前的一个说法

我在交接文档里写过"窗口有界化让 baseline native 更低（84 vs 118MB）"——
那只是 `items` 变短带来的间接效果，**`loaded` 从来没有上界**。
"有界窗口省内存"这个论证站不住脚；它换来的是 4 个位置 bug 和 1 个正反馈环。
真正的内存上界只有两处：解码视图数（`beyondViewportPageCount`）与 `loaded` 的章数上限（待加）。

## 5. Mihon 的参考实现（源码对照，**这一节推翻了我上面的倾向**）

源码：`.research/mihon/app/src/main/java/eu/kanade/tachiyomi/ui/reader/`
（`viewer/pager/PagerViewer.kt`、`viewer/pager/PagerViewerAdapter.kt`、`model/ViewerChapters.kt`）

### 5.1 它的窗口也是"滚动的、有界的"——不是只增不减

```kotlin
data class ViewerChapters(
    val currChapter: ReaderChapter,
    val prevChapter: ReaderChapter?,
    val nextChapter: ReaderChapter?,
)
```

**窗口恰好 3 章**，而且每章是**整章加载**（不是我们那种"页数预算切片"）。
项列表是拍平的：

```
[prev 全部 pages] [ChapterTransition.Prev?] [curr 全部 pages] [ChapterTransition.Next?] [next 全部 pages]
```

R2L 时整个列表 `reverse()`（对应我们的 `reverseLayout`）。

**读者从第 N 章走到第 N+1 章时，窗口整体前滚一格**（prev 变成旧的 curr），
于是**列表前端会丢掉整整一章**——和我们的滑动窗口一样会重编号。
所以：**"只增不减"不是 Mihon 的做法，也不是必需的**；我上一节的倾向（改成只增大表）要撤回。

### 5.2 它凭什么不出 bug：位置用身份 + 变更协议三道闸

| 机制 | 源码位置 | 作用 |
|---|---|---|
| **位置是对象身份** | `private var currentPage: Any?`（`ReaderPage` 或 `ChapterTransition`） | 不是下标；下标只在用到的那一刻由 `items.indexOf(page)` 现算 |
| **① 只在空闲时改数据** | `setChapters()`：`if (isIdle) … else awaitingIdleViewerChapters = chapters`，注释写着 *"otherwise there'd be a noticeable and annoying jump"* | 绝不在滚动/落页过程中换数据 → 不会出现"分页器数字还没跟上就被读走" |
| **② 换数据前后摘挂监听器** | `setChaptersInternal()`：`removeOnPageChangeListener` → `adapter.setChapters(...)` → `addOnPageChangeListener` → **手动** `onPageChange(pager.currentItem)` | 换数据本身**不产生任何"页变了"的事件**；改完主动重同步一次 |
| **③ 用身份重新定位** | `moveToPage(page)`：`val position = adapter.items.indexOf(page)` → `setCurrentItem(position, true)`；`refreshAdapter()`：`setCurrentItem(currentItem, false)` | 列表变了之后，当前位置是"身份 → 新下标"重新算出来的 |
| **④ 框架侧按身份保持可见项** | `getItemPosition(view) = items.indexOf(view.item)`，找不到给 `POSITION_NONE` | ViewPager 自己按身份把正在看的那个 view 留在原位 |
| **⑤ 过渡页不闪** | 只有"章间断层 / `forceTransition` / 邻章未加载完"才插过渡项；`forceTransition = alwaysShowChapterTransition \|\| 当前项就是过渡项` | 过渡项默认是**加载占位**；而且"读者正站在过渡项上"时不会被抽走 |

### 5.3 我们缺的正是这套协议，且我们多长出两个"地雷"

| # | 我们 | Mihon |
|---|---|---|
| 1 | `LaunchedEffect(pagerState, items.size)` 收 **`settledPage`**：`items.size` 一变，effect 重启并**立刻重新发一次当前值**——而此刻分页器可能还是重排**之前**的数字 | 换数据时**摘掉监听器**，不产生事件；改完手动对一次 |
| 2 | 换数据没有任何"等空闲"约束，快滑时照样改 | 只在 idle 时改，否则排队 |
| 3 | 位置用下标 + `reanchorIndex` + `suppressSettleFrom`/`cameFromScrollIntoView` 启发式 | 位置用身份 + `indexOf` + 摘挂监听器 |
| 4 | 窗口形状由**页数预算**决定，边界章的页数是**加载完才知道** → 同一章内窗口就可能变大小 → 多次无谓重排 | 窗口固定 3 章，**只在换章时变** |
| 5 | 过渡项**默认常开**，且归属后一章 | 过渡项默认是加载占位；`forceTransition` 防止脚下被抽走 |

第 1 条尤其致命：它把"重排前的旧数字"当成"读者翻到的位置"回报给状态机，
而下标恰好因为前端丢了一章而 **平移了一整章的量（页数 + 1）**——这正好解释了实测的
"前一章 2 页就偏 3、3 页就偏 4"。

## 6. 修订后的结论

**三种方案的最终对比：**

| | 我的：滑动窗口 + 下标 | 你的：只增大表 + 下标 | **Mihon：滚动 3 章 + 身份位置 + 变更协议** |
|---|---|---|---|
| 窗口是否重编号 | 会（每章一次） | **不会** | 会（每章一次，和我们一样） |
| 位置语义 | 下标 | 下标 | **身份** |
| 数据变更时机 | 随时（含滚动中） | 随时 | **仅空闲；否则排队** |
| 变更时的事件处理 | 靠抑制标志猜 | 靠抑制标志猜 | **摘监听器 + 手动重同步** |
| 内存 | items 有界 / loaded 无界 | items、loaded 都无界 | items 有界（3 章）/ 章对象按需 ref/unref |
| 失败模式 | 静默错页（已发生） | 内存增长（可见） | — |

**结论：不需要改成"只增大表"。Mihon 证明滚动窗口本身没问题。
要补的是"变更协议"这一层，而位置改身份是这套协议的前提。**

（上一节我把"只增不减"当成方向，是因为当时只看到"平移"这一半原因；
读到 Mihon 才确认：**平移是正常的，问题是平移之后没人按身份重新定位、而且变更发生在滚动中**。）

### 6.1 落地清单（按 Mihon 的协议，结合我们的结构）

1. **位置改身份**：`positionKey`（pageId / `transition:from->to`）为真相，
   `currentIndex` 变成派生量。
2. **`items` 变更只在分页器空闲时应用**：滚动中先把新列表挂起（`awaitingItems`），
   等 `pagerState.isScrollInProgress == false` 再换。
3. **变更时抑制 settledPage 的重发**：不要用 `items.size` 当 `LaunchedEffect` 的 key
   去重新收 `settledPage`；换成"变更完成后再主动对一次位置"，
   并且用**期望身份**判定回声，而不是用下标。
4. **窗口形状保持稳定**：不要因为"边界章页数刚量到"就改变窗口大小。
   可以先按章集合决定窗口、并且只在换章时重算（把预算用在**加载**上，而不是用在**显示窗口**上）。
5. **过渡项对齐 Mihon 的语义**：默认常开是我们的选择，那就至少要照搬 `forceTransition`
   ——"读者当前站在过渡项上"时不要把它抽走；并且过渡项的插入条件要能与窗口变化解耦。
6. **`loaded` 加上限**（当前完全没有），只留当前章 ±N 章。

## 2. 已验证的根因

### 2.1 进度恢复失效（#2、并连带 #1）

真机数据库给出了决定性证据：

```
reading_progress: ('3GTS', 'c_99eeba...', pageOrdinal=0)   ← Issue 2，第 0 页
```

`promoteChapter` 里有一句把位置重置成"该章第一页"。读者从 Issue 1 末尾翻进 Issue 2 时
被重置到第 1 页，随后 `saveProgress` 又把 0 写回进度表——**一个重置同时造成"跨章后回到
第 1 页"与"重开回到第 1 页"**。已删除该重置，并把"先记录落点、再判定换章"的顺序调正。

### 2.2 章末过渡页消失（#5）

上一轮为了"保留落点"，`promoteChapter` 改成**按项身份**在新列表里找回位置。但那个身份
**正是过渡项自身**（`item.to` 就是目标章），而过渡项在新列表里位于上一章的页之后，
于是读者被送回上一章，过渡页也看不到。

正确做法：翻过过渡项时落点取**该项在新列表中的下一个位置**，那必然是目标章第一页。
`promoteChapter` 现在接收一个可选的"从哪个过渡项翻过来"参数，据此决定落点。

### 2.3 直接打开 Issue 2 闪退（#4）——OOM，根因在库的解码器

崩溃栈稳定复现于同一位置：

```
java.lang.OutOfMemoryError: Failed to allocate a 8294416 byte allocation
  at com.davemorrissey.labs.subscaleview.decoder.Decoder.init(Decoder.kt:54)
  at SubsamplingScaleImageView$TilesInitTask.doInBackground(SubsamplingScaleImageView.java:2774)
```

反编译 `Decoder.init`（`javap -c`）后确认它的实现方式：

```
InputProvider.openStream()
  → ca.mpreg.imagedecoder.ImageDecoder.Companion.new(stream)     // libvips 系
  → ImageDecoder.decode$default(...) → DecodeResult.getImage(): ByteBuffer
  → ByteBuffer.remaining() → newarray byte                       // 这笔分配就是 8294416
  → getstatic android/graphics/Bitmap$Config.ARGB_8888           // 硬编码，无法改
  → Bitmap.createBitmap([I, w, h, ARGB_8888)
```

三个由此推出的结论：

1. **`setPreferredBitmapConfig(RGB_565)` 对这个 fork 无效**——它内部硬编码 ARGB_8888。
   这解释了为什么把它改成 565 之后，失败分配的字节数与之前**一模一样**（8294416）。
   同理 `setMaxTileSize` 也无效（区域尺寸不经过 Android 的瓦片切分逻辑）。
2. 每载一页都要把**整张图**解码进一个 `ByteBuffer`。3024×1700 在 ARGB_8888 下约 20MB，
   堆上限 256MB，因此"同一页被解码两次"就足以吃掉余量。
3. `ca.mpreg:imagedecoder:9` 是 `com.github.mihonapp:subsampling-scale-image-view` 的
   **传递依赖**，其 native 库 `libimagedecoder2.so` 每种 ABI **16–19MB**
   （四种 ABI 合计约 66MB，这也是 APK 达 90MB 的原因）。

已做的两处修复（都是减少"整图解码"的次数，不是减少单次占用）：

- **同一页只 `setImage` 一次**：用视图 tag 挡住，避免重组或尺寸变化触发第二次整图解码；
- **等布局完成再 `setImage`**：真机日志里出现过 `setImage: 001.jpg view=0x0`，
  尺寸为 0 时库的瓦片初始化行为不可预期。

**未能验证是否真正消除 OOM。** 若仍复现，第 5 节的方案 A 是根治路径。

## 3. 模拟器渲染问题：已判定为模拟器特有

MuMu 上出现过"阅读器打开后页面不画、下层页面内容整体透出"。判定依据与结论：

- **语义树里只有阅读器节点**（完整正确），而**同一时刻的截图**却大部分是下层页面；
- 两次有明确判读规则的实验都是负结果：给根布局染洋红、给引擎视图染青，两者的采样数
  都是 **0**（但顶栏、底部栏、模式 chip 都正常绘制）；绕过 `ReaderDisplayEffects`
  后颜色直方图不变；
- **真机上阅读器完全正常**（`3GTS` / `Issue 1` / `1 / 90`，页面正确显示，无下层透出）。

因此该现象是 MuMu 的合成/截图问题，**不要在它上面继续投入**。
`ReaderChrome` 改用不透明 `Surface` 的那处改动是加固，保留即可。

**因此"数据库缺失导致闪退"这一假设被否掉**：3GTS 的数据是完整正确的。

但查出两个**真实的数据缺口**（与崩溃无关，但影响体验）：

1. **5356 / 5362 个章节的 `pageCount` 为 null**。页数只在"打开过那一章"时回填
   （`ImageDirectoryPageSource.pages()` 之后由 `updateChapterPageInfo` 写入）。
   所以详情页要用户逐个点「更新章节」才看得到页数——用户说的
   "更新章节理应能获取页数"没做到。
2. **44 部漫画声明 `chapterCountKnown = 1` 但实际章节数不符**；
   **4 部漫画的 `coverChapterId` 指向已不存在的章节**（封面会退化）。

注意核查时用到的快照提取踩过一次坑：设备在 `adb exec-out` 传输中途离线，得到一份
**被截断的 3MB 文件**，SQLite 报 `database disk image is malformed`。
那不是设备上的真损坏，是坏拷贝。提取数据库要连 `-wal`/`-shm` 一起取，并确认大小合理。

## 5. 待办（按优先级）

### A. 根治 OOM：控制送进引擎的像素量（已实现，未验证）

先记录一条**排除了的路径**：`SubsamplingScaleImageView` 的 `decoder` 字段是
private 且无公开 setter，而 `TilesInitTask.doInBackground` 里是**硬编码**
`new com.davemorrissey.labs.subscaleview.decoder.Decoder(...)`，没有任何工厂或扩展点
（`javap -c` 已确认）。因此**除了反射没有干净的注入点**；反射的代价是依赖私有字段名，
而 release 构建的 R8 可能改名，所以不采用。

已实现的方案走**公开 API**：`ImageSource.provider(InputProvider)` 是公开工厂，而
`Decoder.init` 只通过 `InputProvider.openStream()` 取图。因此在
`buildImageSource` 里：

- 先用 `inJustDecodeBounds` 读尺寸；
- 长边超过 `MAX_ENGINE_LONG_EDGE = 3000` 时才按 2 的幂降采样，
  再把降采样结果编成 PNG（无损，避免二次 JPEG 损失）包进 `InputProvider`；
- 立刻回收中间位图，否则峰值会变成"位图 + 库的整图解码"两份；
- 不超过阈值时**原样把流交给库**，一个字节都不多搬。

阈值取 3000 的依据：真机屏宽 1440，库的 `minimumTileDpi(180)` 在 1440 宽下要的瓦片
也在这一量级；而绝大多数漫画页长边不超过 3000，因此**这条路径通常根本不触发**。
只有超大跨页才被采样，而那种图原本就是 OOM 的来源。

代价是超大跨页放大后的清晰度下降。**未在设备上验证是否真正消除 OOM。**

### A2. 若 A 仍不够：反射注入自定义 `ImageRegionDecoder`

接口是公开的（`init(Context, InputProvider): Point` / `decodeRegion(Rect, Int): Bitmap?` /
`isReady()` / `recycle()`），自实现可用 `BitmapRegionDecoder` 走**真正的区域解码**，
内存只与区域大小相关，并且能用 `RGB_565`；顺带能去掉 66MB 的 native 依赖
（`libimagedecoder2.so`，每 ABI 16–19MB，是 APK 达 90MB 的来源）。
需要 try/catch 回退，且换库版本时必须重新核对私有字段名。

### A3. 另一条无损路径（未评估完）

`ImageSource.provider { FileInputStream(tempFile) }`：自己把页图复制成临时文件，
让库拿到**可随机访问**的输入。库内部本来也会为 `inputStream` 落临时文件，所以能否
因此改用区域解码、从而避免整图解码，需要在库源码里确认后再说。这条路不损失清晰度，
若成立比 A 更好。

### B. 章节页数在枚举时就回填

现在页数只在"打开那一章"时写入（`ImageDirectoryPageSource.pages()` 之后由
`updateChapterPageInfo` 回填），因此 **5356 / 5362 个章节的 `pageCount` 是 null**，
详情页要用户逐个点「更新章节」才看得到页数。应在章节同步（`MangaChapterSyncer`）
或详情页加载时对未回填的章节列一次页并写入，但**必须限流**，
否则打开详情页会枚举整部漫画。开发文档 6.1 第 3 步本来就要求
"深入：打开详情/更新章节时枚举该漫画章节"。

### C. 清理两处数据缺口

- **44 部漫画声明 `chapterCountKnown = 1` 但实际章节数不符**：可能是重扫与深度同步的
  交错写入。需要先定位是哪个路径写坏的，再修；不要只做一次性数据修复。
- **4 部漫画的 `coverChapterId` 指向已不存在的章节**：封面取不到时应回退到
  该漫画任一可用章节的第一页。

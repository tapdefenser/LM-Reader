## 四、已经查清并修掉的根因（附证据）

### 1. 跨章落点与进度恢复失效（同一根因，现已随重做消失）

当时的 `promoteChapter` 里有一句把位置重置成"该章第一页"。真机数据库佐证：

```
reading_progress: ('3GTS', 'Issue 2', pageOrdinal=0)   ← 读者读到第 3 页，存的却是第 0 页
```

一个重置同时造成"跨章后回到第 1 页"与"重开回到第 1 页"。

**注意这里出过两次回归**：先改成"按项身份找回位置"，而那个身份**正是过渡项自身**；
再改成"过渡项的后继"，又发现窗口变化会让过渡项本身从新列表里消失。

这两个回归说明的其实是同一件事：**只要还在"提升章节 + 重建列表"，落点就必须在两套下标
之间换算，而换算依据（项身份）本身就随列表变化。** 现在的做法是根本不重建列表，因此
"落点"这个概念不存在了——翻页就是移动一格（见第五节）。

### 2. 直接打开章节闪退 = OOM，根因在库的解码器

崩溃栈稳定：

```
OutOfMemoryError: Failed to allocate a 8294416 byte allocation
  at com.davemorrissey.labs.subscaleview.decoder.Decoder.init(Decoder.kt:54)
  at SubsamplingScaleImageView$TilesInitTask.doInBackground(:2774)
```

`javap -c` 反编译得到的结论：

- `Decoder.init` 无条件调用 `InputProvider.openStream()`，把**整张图**解码进一个 `ByteBuffer`
  再转 byte[]；那笔 8294416 字节就是它。
- 位图格式**硬编码 `ARGB_8888`**，因此 `setPreferredBitmapConfig(RGB_565)` 与
  `setMaxTileSize` 对它**完全无效**——这解释了为什么改成 565 后失败字节数一模一样。
- `TilesInitTask` 里是硬编码 `new Decoder(...)`，`decoder` 字段 private 无 setter，
  **除了反射没有干净的注入点**。
- 该解码器来自传递依赖 `ca.mpreg:imagedecoder:9`，native 库 `libimagedecoder2.so`
  每种 ABI 16–19MB（四 ABI 约 66MB，是 APK 达 90MB 的来源）。

已做的三层降内存（**未验证是否消除**）：同一页只 `setImage` 一次、`doOnLayout` 后载图、
超过长边 3000 的页先降采样再编码成 PNG 交给库（走公开的 `ImageSource.provider`）。

### 3. 详情页看不到页数 = 数据缺口（已定位并部分修复）

按卡片可用性拆分后的实际规模：

| pageCount | AVAILABLE | STALE |
|---|---|---|
| 未回填 | **4698** | 658 |
| 已回填 | **6** | 0 |

可读的 4704 个章节里只有 6 个有页数。原因是页数只在"打开过那一章"时写入。
已实现**按需、有上限**的回填（每次进详情页最多补 8 章）。

### 4. 被否掉的假设（避免重复调查）

- **数据库没有结构性损坏**：孤儿章节、重复 `documentId`、失效进度引用、越界页码全为 0；
  3GTS 两章数据完全正确。所以"数据库缺失导致闪退"不成立。
- **44 部"章节数声明不符"全部是 `STALE` 卡片**（界面不显示），属历史遗留。
- **`coverChapterId` 失效只有 4 部**。
- **模拟器渲染问题（页面不画、下层透出）是 MuMu 特有**：语义树里只有阅读器、
  而截图却大部分是下层页面；给根布局染洋红、给引擎视图染青的采样数都是 **0**；
  **真机上阅读器完全正常**。不要在此继续投入。

## 五、跨章编排：这一轮查清的真实结构

这一轮在跨章上连续踩了五个坑，每个都只在真机/逐页点按时才暴露。**先读这一节**，
否则很容易重犯（前四个坑我各犯过一次以上）。

### 5.1 项列表的形状（当前实现）

```
… issue1 的页、[过渡页]、issue2 的页、[过渡页]、issue3 的页 …
```

**过渡页只是这条线上的一个普通位置**，和"一页图"本质相同——只是显示的不是图片而是
"已读完 issue1 / 下一章 issue2"。因此：

- **翻页就只是前后移动一格**。滑动、点按区域、音量键、滑杆、上一章/下一章按钮全部
  汇聚到 `move(delta)`；当前在哪一章由"当前项属于哪一章"反推。
- **没有"跨章"这个事件**，也没有"提升章节"。这是本条设计的全部要点。
- **过渡项没有方向**：`ReaderItem.Transition` 里没有 `forward`，键只由前后两章决定，
  往前翻与往后翻遇到的是同一个项。
- **它归属后一章**。这样同一个边界在任何窗口下键都一样；若归属前一章，旧窗口里后一章
  还没加载出来时过渡项根本不存在，键就无从比较。
- **窗口在阅读过程中固定**，只在读者走到边缘章时才向那一端补一批。补的时候按项身份
  重新定位（`reanchorIndex`），因此画面不跳。**因为窗口不重建，所有项的下标不变，
  "翻页跳到别的页"在结构上不可能发生。**

### 5.2 列表里只放"已知页数"的章

还没加载完的章**完全不出现**：既不贡献页，也不贡献过渡页。否则会插出一个悬空的过渡页
（甚至两个过渡页挨在一起）——读者会看到一个说不清"通向哪里"的过渡页。

加载完成后它的页与过渡页一起插入，此时按页身份重新定位，画面不跳。

### 5.3 预载预算与窗口扩张

- 「预载页数」默认 9，**过渡页也算一页**：跨一章的代价 = 1（过渡页）+ 该章页数。
- 页数未知的章是**边界章**：必须放进来并要求枚举一次，否则第一部打开的漫画会因为
  "谁都不知道有几页"把窗口算成空的，末页只能显示"已是最后一章"而后面其实还有几十章。
- **边界章必须同时被加载**（`chaptersToLoad`）。曾经出现过"规划算出了边界章、但没人去
  加载它"，于是它的页数永远未知、窗口再也长不起来——真机上表现为只剩当前章。
  规划与加载因此共用 `planFor` / `chaptersToLoad` 一对函数。
- 末章判定用**整部的最后一章**，不是窗口的最后一章。用窗口会插出一个过早的
  "已是最后一章"。

### 5.4 已废弃的方案（不要回去）

前四版都栽在同一个念头上：**把"跨章"当成事件**。曾经有过的、现在全部删掉的机制：

| 删掉的机制 | 它造成的问题 |
|---|---|
| `promoteChapter`（碰到过渡页就提升章节、重建列表） | 下标整体变化而分页器停在旧下标 → **跳页** |
| `landingAfterTransition` / `resolveLanding`（在两套下标间换算落点） | 换算一错就落到不相干的页 |
| `forward` 方向标志 + 两套过渡项 | 同一边界两个键，窗口一变就找不到 |
| `pauseOnChapterTransition`（到达后停不停的开关） | 新模型里过渡页本来就占一格，开关没有意义 |
| `sanitized()` 脏窗口校正 | 窗口不再被重建，就没有"脏窗口" |
| 分页器的"程序化滚动抑制" | 不再重建窗口 → 不需要把位置挪来挪去 |
| `pastStartChapter`（往回翻越界时提升上一章） | 不存在"越界"这件事，往回翻就是上一个项 |

净减 713 行。**如果你发现自己在加回其中任何一个，先回来读这一节。**

## 八、工作方式上值得注意的几点（避免重犯）

1. **取设备数据库的 `exec-out` 路径不稳定**，会静默截断成残片并报
   `database disk image is malformed`。**校验 `PRAGMA integrity_check` 再用**，
   否则会把坏拷贝当成设备真损坏（我误判过一次）。
2. **改代码前先确认改的是哪一层**。我在跨章落点上连续改错两次：
   第一次猜"身份会丢失"（其实不会），第二次"按身份找回"（身份就是过渡项）。
   最终靠**加单测**才发现真实结构（过渡项只插在当前章之后，往回翻走的根本不是过渡项）。
3. **"状态被写坏"比"算法算错"更常见，而且更难看出**。本轮五个坑里有四个是并发写入
   与快照过期造成的，症状全都伪装成"落点算错了"。可复用的判别方法：
   **打印出实际的窗口与项列表**（而不是只看屏幕），一看形状就知道是哪一类。
   我前面花在推理上的时间远多于加上那两行日志之后花的时间。
4. **不要用"全局记住上一次的值"来去重**。`lastSettledIndex` 那版把读者恰好翻到我们
   曾挪到过的位置也一并丢掉了；正确的做法是在**能区分来源的那一层**去抑制
   （分页器知道哪次滚动是自己发起的）。
5. **先量规模再判断严重性**。"5356 个章节没有页数"听起来像脏数据，
   按可用性拆开才发现是**可读内容上的 4694 个缺口**，性质完全不同。

# 阅读器逻辑总览（以当前代码为准）

这份文档只讲**现在的实现**，不讲历史方案。历史坑见 `交接-新对话接手.md`。
读代码时的入口顺序：`ReaderViewModel` → `ReaderChapters` → `PagerReader` / `StripReader` → `ReaderImageView`。

---

## 0. 一句话

**阅读器里只有一条线，跨章不是事件，只是线上的一个位置。**

```
… ch1 的页、[过渡页]、ch2 的页、[过渡页]、ch3 的页 …
```

翻页、滑动、点按区域、音量键、滑杆、「上一章/下一章」——**全部**归结为同一个动作：
把 `currentPageIndex`（这条线上的下标）加减若干。当前在哪一章，是**反推**出来的，不单独维护。

---

## 1. 三条定律

后面所有细节都是这三条的推论。改代码时先对照它们。

| # | 定律 | 违反它会怎样 |
|---|---|---|
| **L1** | **只有一条线**：章、页、过渡页都只是线上的位置；没有"跨章事件" | 一旦把跨章当事件去重建列表，就会出现跳页、卡住、"有时进下一章有时被送回上一章" |
| **L2** | **`items` 是派生量，不是真相**。真相是 `chapterList`（目录）+ `loaded`（已加载页清单）+ `currentPageIndex`（位置） | 直接改 `items` 而不改真相，下一次重排就会把它抹掉 |
| **L3** | **窗口只依赖"当前章 + 设置 + 已加载章的页数"，不依赖页码** | 窗口依赖页码 → 页码抖动改变窗口 → 窗口改变又让下标抖动 = 正反馈环（曾经每秒重建 80 多个视图，见 `交接` 第五节第 6 条） |

## 2. 数据分层

### 2.1 三种"章"

| 类型 | 含义 | 来源 |
|---|---|---|
| `ChapterRecord` | 目录里的一章（id、标题、排序键、页数声明…） | 数据库，`chapterList` |
| `ViewerChapter` | **已经被页源枚举出页清单**的章：`chapter` + `pages` + `source` + `state` | `loaded`（按 chapterId 索引） |
| `ViewerChapters` | **窗口**：`window: List<ViewerChapter>` + `currentIndex`（当前章在 window 里的下标） | 每次重排现算 |

`ViewerChapter.LoadState` 有三态：`LOADING` / `Loaded` / `FAILED`。
`isUsable` = `Loaded` 且 `pages` 非空——**只有 usable 的章才会出现在项列表里**。

### 2.2 项（`ReaderItem`）

只有两种：

```kotlin
PageItem(page, chapter)                 // 一页图
Transition(from, to)                    // 夹在两章之间的那一张
```

- `Transition` 的 `key` 是 `"transition:{from}->{to}"`，**没有方向**——往前翻和往后翻遇到的是同一项。
- `Transition.to == null` 表示"整部的终点"（"已是最后一章"）。
- `Transition.chapterId` 取**后一章**（`to ?: from`）。这样它在任何窗口下都算出同一个 key，
  但**"落在过渡页上"不等于"已进入下一章"**——这条区别是 `chapterEnteredBy` 的全部内容（见 §6.3）。

### 2.3 状态（`ReaderUiState`）

```kotlin
chapterList: List<ChapterRecord>   // 真相：全部章节
loaded: (在 ViewModel 里，不在 state) // 真相：已加载页清单
items: List<ReaderItem>            // 派生：窗口里 usable 章的页 + 过渡页
currentPageIndex: Int              // 真相：在 items 里的绝对下标
chapters: ViewerChapters?          // 派生：当前窗口 + 当前章在窗口里的下标
```

**必须记住的两套下标，别混**：

- `currentPageIndex` —— 在 **`items`** 里（跨章连续，含过渡页）
- `chapters.currentIndex` —— 在 **`window`** 里（只数章，不数页）

派生快捷属性（都在 `ReaderUiState` 里）：`currentChapter`、`currentPages`、`localPageIndex`
（落在过渡页上为 **null**）、`currentPageCount`、`currentItemIsTransition`、
`hasPreviousChapter` / `hasNextChapter`。

## 3. 一次完整的打开时序

```
ReaderScreen 创建 ReaderViewModel(mangaId, chapterId, startPage?)
  └─ init: 订阅 readerPreferences.settings（变了且涉及过渡页/预载 → rebuild）
  └─ reload()
       1. getBackfillTarget(mangaId) → { manga, chapters, sourceTreeUri }
       2. savedProgress = progressRepository.get(mangaId)
       3. 读出这部漫画的阅读模式/方向覆盖，与全局设置合并 → settings
       4. 决定"打开哪一章"：
            详情页指定了章节 → 用它
            入口是 RESUME_CHAPTER → 用 savedProgress.chapterId，否则第 0 章
       5. 决定"打开哪一页"（优先级）：路由带来的 startPage > 该章的进度页 > 0
       6. openAt(index, page)
```

`openAt` 做的事（**只有"用户主动跳章"才走这里**，翻页不走）：

```
loadChapter(record)                     // 枚举这一章的页清单
loaded[chapterId] = current
fillWindow(chapterId)                   // 只建窗口、算位置（此时只加载了当前章）
currentPageIndex = 该章第一页 + page    // 落到指定页
updateChapterPageInfo(...)              // 回填页数与封面
saveProgressAt(当前项)                   // 落一次进度
loadNeighbors()                         // 把规划出的邻章排上加载
warmPrefetch()                          // 排磁盘预取
```

## 4. 窗口：阅读器的"可见世界"

### 4.1 为什么必须有窗口

- 整部漫画全进 `items`：上千章会把整个目录的页清单堆进列表（内存与 `nearWindowEdge` 都失效）。
- 只放当前章：跨章时下一页还不存在，读者会卡在章末。

所以窗口 = **当前章 ± 规划范围内、且已经加载好的那些章**。

### 4.2 `planFor`：预算怎么算

「预载页数」是**格数**预算（过渡页也算一格），默认 9：

```kotlin
prefetchBudget(total) = PrefetchBudget(forward = total / 2, backward = total - total / 2)
// 9 → 往后 4、往前 5（余数给"往前"，因为往前第一步常常要先跨一个过渡页）
```

`PreloadPlan.compute` 从当前章向两侧走：

```
从当前章出发，distance = 1,2,3…
   index 越界 → 停
   该章页数未知（边界章）→ 收进来，停
   预算不够跨这一章（remaining < 1 + 该章页数）→ 预算还有剩就收进来，停
   否则 remaining -= (1 + 该章页数)，收进来，继续
```

两个上限：`MAX_PRELOAD_CHAPTERS_PER_SIDE = 3`（单侧最多 3 章）、预算耗尽。

**注意：这个预算决定"窗口里放几章"，不决定"内存里放几页图"。** 后者由渲染层的
`beyondViewportPageCount` 决定（见 §8.2）。两者数值上相关但机制完全不同——
把它们混起来看会得出错误结论（我因此误判过一次）。

### 4.3 边界章（frontier）

规划用的是**已知页数**，而一章的页数要等它加载完才知道。于是"刚量到页数的章"会立刻改变
规划结果。为了保证窗口不会一直比预载进度慢一步，`planFor` 在两侧**额外补一格边界章**：

```kotlin
nextFrontier = (next.lastOrNull() ?: currentIndex) + 1
if (nextFrontier in list.indices && next.size < MAX) next += nextFrontier
```

它**同时必须被加载**（`chaptersToLoad` 会带上它），否则它的页数永远未知、窗口再也长不起来。

### 4.4 `buildWindow`：有界 + ±1 保险

```kotlin
wanted = { currentIndex } ∪ plan.nextIndices ∪ plan.previousIndices
lo = min(currentIndex - 1, plan.previousIndices.minOrNull() ?: currentIndex)
hi = max(currentIndex + 1, plan.nextIndices.maxOrNull() ?: currentIndex)
window = [lo..hi] 内【且 loaded 里已有】的章，按目录顺序
```

- **范围之外不放**：窗口始终约等于预载范围那么大，而不是"读过多少章就有多少章"。
  放掉只是不显示，页清单仍在 `loaded` 里，往回翻立刻可取回、不重新读盘。
- **±1 不能省**：过渡项只有"后一章也在窗口里"才会生成（`items()` 里 `index > 0` 才插）。
  少了这一格，读者翻到本章末页会**直接卡住**，既过不去也没有"到底了"的提示。
- 返回 `window` 与"当前章在其中的下标"。

### 4.5 `writeItems`：窗口没变就**什么都不做**

```kotlin
sameWindow = 旧 window 的 chapterId 序列 == 新 window 的 chapterId 序列
if (sameWindow) 只同步 chapters.currentIndex（连 items 实例都不换）
else           items = chapters.items(...) + reanchorIndex(...)
```

**为什么这条很关键**：`items` 一变，分页器就要重新布局，而它的「滚动偏移 ↔ 下标」映射在
**右到左**（`reverseLayout`）下会抖一格。这一格足以让落页回报指到相邻的另一章，从而
"当前章翻转 → 窗口重算 → 表长变化 → 再抖一格"形成每帧一轮的环。窗口等价时连实例都不换，
就杜绝了这种无谓重排。

## 5. 加载链

```
rebuild() = fillWindow(当前章) + loadNeighbors()
            └ 重排窗口            └ 把规划出的章排上加载
```

**这两件事必须一起做**。曾经 `rebuild()` 只重排窗口不排加载，于是加载链只在
"上一章加载完成"时前进一次：进入第 1 章请求了 2/3/4，三章完成后 `chaptersToLoad` 仍返回
2/3/4（已在 `loadJobs` 里被跳过）→ 链断掉 → 读者被永久关在最初的 4 章里。

```
chaptersToLoad = plan.nextIndices + plan.previousIndices.asReversed()
```

`loadOne(record, treeUri)` 的两个守卫**语义不同，都不能省**：

| 守卫 | 含义 | 省略会怎样 |
|---|---|---|
| `loadJobs.containsKey(id)` | 这一章**正在**加载，别重复排队 | 同一章被并发枚举 |
| `loaded.containsKey(id)` | 这一章**已经有结论**（成功**或失败**） | 每次 rebuild 都重试失败章 → 无限重试 |

完成后：`loaded[id] = result ?: FAILED 占位` → `rebuild()` → `warmPrefetch()`；
`finally` 里 `loadJobs.remove(id)`（**不移除的话 `loadJobs` 会悄悄变成"曾经请求过"的集合**）。
`loadJobs` 的加载在 `viewModelScope` 上，`onCleared()` 时全部 cancel。

失败章只能由 `retryFailedChapters()` 显式重来：它先从 `loaded` 里**摘掉**失败结论，再取消任务、
重新 `loadOne`。失败章可能已经不在窗口里（读者翻过去了），所以按 `loaded` 里的失败项扫，不只扫窗口。

## 6. 位置：move / settleAt / 锚定

### 6.1 移动

```kotlin
fun move(delta: Int) {
    target = (currentPageIndex + delta).coerceIn(items.indices)
    if (target == currentPageIndex) return      // 已在端点，什么也不做
    settleAt(target)
}
```

所有输入汇聚到这里：点按分区（`NavigationRegions.hitTest` → MENU / PREVIOUS / NEXT / PAN）、
音量键、滑杆、页码指示。

### 6.2 `settleAt(absoluteIndex)`

```
1. 越界 → return
2. absoluteIndex == currentPageIndex → return        // 分页器回放自己造成的位置
3. currentPageIndex = absoluteIndex
4. entered = chapterEnteredBy(item)                  // 见 §6.3
5. 若是 PageItem → saveProgressAt(item)               // 只有页才写进度
6. entered != null 且 != 当前章 → chapters.currentIndex = 该章在窗口里的下标
7. 若"换了章" 且 nearWindowEdge() → rebuild()
```

第 7 步的 `chapterChanged &&` 不能省：窗口只依赖当前章（L3），**同章内翻页不需要重新规划**。
`nearWindowEdge()` = 当前章在窗口里的下标 `<= 1` 或 `>= size - 2`（`WINDOW_EDGE_MARGIN = 1`）。

### 6.3 `chapterEnteredBy(item)`：过渡项**不算**换章

```kotlin
if (item is PageItem) item.chapterId else null      // 过渡项 → null = 不换章
```

理由：`Transition.chapterId` 取后一章（为了 key 稳定），但"站在两章之间那一张上"不等于
"已经进入下一章"。用它当判据会让当前章在边界上被反复翻转，与分页器那一格抖动合成环。
不换章也不会把跨章读卡住——下一章本来就被边界章规则收进窗口并加载好了。

### 6.4 锚定（`reanchorIndex`）

窗口重排会把新章插到列表前面或后面，于是**下标整体平移**。重建时必须按**项身份**
（`ReaderItem.key`）把读者放回原处：

```kotlin
anchorKey = 旧 items[旧下标].key
新下标 = 新 items 里 key 相同的那一项；找不到就 coerceIn
```

**这是"补窗口时画面不跳"的唯一保证**，每次重建都必须经过它。

### 6.5 分页器侧的位置同步（`PagerReader`）

两套机制互相配合，且**必须互相抑制**，否则会来回撞墙：

| 机制 | 作用 |
|---|---|
| `LaunchedEffect(positionKey)` → `scrollToPage(currentIndex)` | 外部位置变化（点按、滑杆、恢复进度、换章落点）驱动分页器滚动。key 用**当前项的身份**而不是"下标+项数"——窗口重排会让下标变而项数不变 |
| `snapshotFlow { settledPage }` → `onItemSettled` | 分页器自己落页后回报给状态机 |
| `suppressSettleFrom` | 记下"我们自己挪到的目标"：只有分页器**落到别处之后**同一个位置再次出现，才算读者翻页 |
| `cameFromScrollIntoView` | 归位引起的滚动不算读者翻页 |

条漫（`StripReader`）用 `visibleItemsInfo`（不是 `firstVisibleItemIndex`）判断当前项，
并用 `pageHeights`（每页实测高度）做滚动定位。

## 7. 预取（只落磁盘，不压堆）

`warmPrefetch()` 从 `currentPageIndex` 出发，沿 `items` 向前/向后走，
**每遇到一项消耗一格预算**（过渡页也占一格），收集 `PageItem` 交给 `PagePrefetcher`：

```
prefetcher.request(scopeKey = mangaId|窗口首章|窗口尾章, ahead, behind)
```

- 直接按项序走，所以"跨章正确"是免费的，不需要分章计算。
- `scopeKey` 变了才清理旧缓存文件（翻页不改 scopeKey，因此同章内翻页不会反复删缓存）。
- 缓存上限 192MB（磁盘）、单页 24MB，超出按最早写入淘汰。
- **命中预取时渲染层直接读磁盘字节**，省一次 SAF 的跨进程读取。

## 8. 渲染层

### 8.1 两套渲染器

| 阅读模式 | 渲染器 |
|---|---|
| 左到右 / 右到左 / 竖向分页 | `PagerReader`（`HorizontalPager` / `VerticalPager`，整页吸附） |
| 条漫 / 条漫带间隔 | `StripReader`（`LazyColumn` 连续滚动） |

`key(state.readingMode)` 包住整棵树：模式切换＝换一套实现。
**`currentChapterId` 绝不能进这个 key**——它正好在跨章那一刻变化，会把整棵树销毁重建，
于是读者正在看的那一页也被重新解码 = "跨章闪黑一帧"。

### 8.2 同时保留几页已解码（内存上界的真正来源）

```kotlin
adjacentPagesAlive = (settings.preloadPages / 4).coerceIn(0, 2)   // 默认 9 → 2
HorizontalPager(beyondViewportPageCount = adjacentPagesAlive)     // 竖屏分页用 0
```

即**同时约 5 个引擎视图**（可见 1 + 两侧各 2）。
每页解码后是整张位图（ARGB_8888），因此内存 ≈ 存活视图数 × 每页整图 + 基线。

> ⚠️ 竖屏分页的 `beyondViewportPageCount = 0`，与横向不一致：竖屏翻页更容易看到"落页那一帧还空着"。

### 8.3 `EnginePageView`：一页一个引擎视图

- `remember(page.pageId)` 持有视图；**页码身份变了就换新视图**（库内部持有瓦片与缩放状态，
  复用实例会串页）。
- 等 `doOnLayout` 有尺寸才 `setImage`，且用 `IMAGE_LOADED_TAG` 保证**同一页只 `setImage` 一次**
  （每次 `setImage` 都是一次整图解码）。
- `DisposableEffect.onDispose` 里：先摘监听器 → 清 tag → `recycle()` → `view = null`。
- `buildImageSource`：命中预取就用磁盘字节；否则先只读尺寸（`inJustDecodeBounds`），
  **长边 > 3000 先按 2 的幂降采样再编 PNG**——因为引擎的 `Decoder.init` 会无条件整图解码
  且硬编码 ARGB_8888（`setPreferredBitmapConfig` / `setMaxTileSize` 对它无效）。
- 引擎配置对照 Mihon：双击缩放、`PAN_LIMIT_INSIDE`、`minimumTileDpi(180)`、
  缩放类型 6 种映射、`setCropBorders`、起始缩放位置。

## 9. 进度

- **只存页码**，`intraPageRatio` 恒为 0（照搬 Mihon：恢复时对齐页顶）。
- `saveProgressAt(item)` 只对 `PageItem` 生效——**落在过渡页上不写**（那不是某一页）。
- 写入经 `progressSaveMutex` 串行化；离开阅读器、每次落页、打开时各写一次。
- `savedProgress` 同时保留 `read` / `bookmark` 标志，读取时原样带过去。

---

## 10. 设置与模式

- 全局设置在 `ReaderPreferences`；**这部漫画可以覆盖阅读模式与方向**（存在 DB 里）。
  合并规则：`global.withMangaOverride(mode, orientation)`；每次设置流发射都用当前覆盖重新叠加。
- 改变"过渡页开关"或"预载页数"会触发 `rebuild()`（前者改项列表，后者改窗口）。
- 点按分区有两套（分页 / 条漫），`DEFAULT` = 跟随模式（竖向给 L 形，其余给左右两栏）。
- 每次切换阅读模式会显示一次点按区域提示（`showTapZoneOverlayOnce` 可关）。

---

## 11. 不变量清单（改代码时逐条对照）

1. 只有一条线；`move(delta)` 是唯一的移动入口（`openAt` 只用于主动跳章）。
2. `items` / `chapters` 都是派生量；改窗口只能通过 `fillWindow` → `writeItems`。
3. 窗口只依赖当前章 + 设置 + 已加载页数；**不能让页码影响窗口内容**。
4. 任何重排后都要过 `reanchorIndex`；一切定位用项身份，不用下标。
5. 窗口必须包含当前章前后各至少一格（否则过渡项缺失，跨章卡死）。
6. 已加载的章不重复加载；失败章只由 `retryFailedChapters` 显式重来。
7. `rebuild()` 必须同时"重排窗口"和"排加载"。
8. 过渡项不算换章；`Transition.chapterId` 只用于 key 与显示。
9. 同一页只 `setImage` 一次；窗口等价时 `items` 实例不换。
10. 预载预算是**格数**，与"内存里几页图"无关。

## 12. 已知粗糙点 / 小 bug 高发区

按"最可能出问题"排序，供定位参考：

| 位置 | 可能的表现 | 机理 |
|---|---|---|
| 顶栏章节名 / 页码指示 / 滑杆 | 站在过渡页上时显示的章名是**上一章**，页数置灰 | `chapterEnteredBy` 让当前章保持上一章；过渡页本身显示的文字来自 `Transition.from/to` |
| 滑杆 `jumpToPage` | 拖了没反应 | 它要求当前章 `pages.indices` 内且 `indexOfFirstPageOfChapter >= 0`；当前章不在窗口里时静默 return |
| 「上一章 / 下一章」按钮 | 与翻页行为不一致 | 它走 `openAt`（重建窗口、丢页内位置），而翻页走 `settleAt` |
| `showChapterTransitions = false` | 章与章直接相接 | 没有过渡项，"到底了"标记与跨章判定都只剩 PageItem 路径，容易出现"少一格"的观感差异 |
| 竖屏分页 | 落页那一帧可能还空着 | `VerticalPager` 的 `beyondViewportPageCount = 0`，与横向不一致 |
| 条漫定位 | 恢复进度后落点偏一点 | 落点判定用 `visibleItemsInfo` + 实测页高，页高未测全时是估算 |
| 窗口大小 | 打开时窗口可能先 3 章后 4 章 | 边界章页数未知 → 规划偏保守；加载完重算后变宽（这是设计内的，但观感上像"闪一下"） |
| 模式切换 | 切换后回到当前页而不是页内位置 | `key(readingMode)` 重建整棵树；页内位置本来就不存（page-only） |
| 预载页数调小 | 窗口可能变小、已加载的章被移出窗口 | `buildWindow` 有界化的直接结果（页清单仍在 `loaded`，往回翻不会重读） |
| ARCHIVE / 单章节 | 相关路径未实现或未验证 | ZIP/CBZ 页源未实现；单章节模式的窗口只有一章 |
